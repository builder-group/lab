# Architecture

How MidiMarble v4 is built. Product behavior is in [ux.md](ux.md), target films in [references.md](references.md).

## Stack

- **Host:** Tauri 2 on macOS, started from the community `desktop-tauri` template. The Rust host owns files, packages and processes: Blender, FFmpeg and the agent CLIs.
- **UI:** React, TanStack Router and Tailwind, structured by the community [React project structure](https://github.com/builder-group/community/blob/develop/docs/conventions/project-structure-react.md). The Rust side follows the [Rust project structure](https://github.com/builder-group/community/blob/develop/docs/conventions/project-structure-rust.md).
- **State:** `feature-state` atoms and `Cx` owners following the lab rules
- **Track view:** Three.js
- **Physics:** Rapier's deterministic WASM build (`@dimforge/rapier3d-deterministic-compat`) in a Web Worker. The same simulation module runs headless in Node for tests and fixtures.
- **Documents:** JSON validated with Zod and versioned with [`versjon`](https://www.npmjs.com/package/versjon), so an old file fails with a clear message
- **Blender:** a bundled Python worker started as a dedicated Blender process. The app never installs a Blender add-on or changes Blender preferences.

## Units and time

Distances are meters and angles are radians, matching Blender. New projects use a kit 1.5 times the Marble Race Kit (`KIT_SCALE` in `simulation/pieces.ts`): 24 mm marbles (`DEFAULT_MARBLE_RADIUS`) and platforms 3 cm long, 1.2 cm thick and 15 cm deep, with every other piece default scaled alike. `PLACEMENT_LENGTH` (9 cm) spaces hops and columns, and colliders keep a fixed depth (`COLLIDER_DEPTH`, 4.5 cm), so Depth is visual. The camera defaults are 30 mm, tilt 0.54, Turn 90° and 48 cm (`references.md`). Time is seconds on one shared timeline. Physics runs at a fixed 240 Hz; render frame rates are derived from it at export.

## Data model

The project document is plain typed records, in `project/schema.ts`. Behavior lives in plain modules that read and write them; nothing in the file is a class. One rule splits it: nothing in `film` can change how a marble runs, so the simulation has no reason to read it. `createPlan` and `simulate` take `TRunInput`, which leaves `film` out, so the compiler proves the rule, and a test with randomized `film` values checks the result stays identical. Build Track is the exception by decision: an assist that makes pieces may read the camera through `frameBand` to fit the frame.

```ts
Project { $schema: 'marble-project@6', id, title, revision, format, length, gravity, songs, marbles, track: { pieces, groups }, film }
Song    { id, name, kind, path?, start, tempo?, backing, backingSound? }   // any number
Marble  { id, name, labelColor, sound, radius, start: { position, time, velocity?, spin? }, skin?, hits }
Hit     { id, time, pitch?, velocity?, duration?, songId? }
Piece   { id, name?, labelColor?, type, layout?, params, angle, place, path?, skin?, ride? }
Group   { id, name, marbleId?, pieceIds, pattern?: { kind, hitIds, width, bounce, maxTilt? } }
Film    { theme, themes, wall, lights, decor, madeInBlender, titles, quality, camera }
```

A skin holds an asset ID (optional) and property overrides: `colorSource`, `onHit`, `glowColor`, `variant`, `properties`, on pieces and marbles. A `ride` is the ride a marble took along a rail, relative to where it entered. A title is `{id, name?, labelColor?, text, font, size, color?, in?, out?, style?, plate?, position, angle}`.

A piece's `place` is exactly one of three, and `simulation/attach.ts` converts between them while keeping its world pose (each helper returns `{entity, commands}` with one `addPiece` command). `tieOf(piece)` gives the tie or null, and `freePosition(piece)` a free piece's position.

- **`free`:** `{kind: 'free', position}`. Environment the marbles may strike.
- **`follows`:** `{kind: 'follows', marbleId, hitId, contactAt?, offset?, held?}`, for scenery types and any piece a person ties to a marble's moment. The piece enters the run at the hit time plus its `entryDelay` param (up to `ANCHOR_DELAY`, 10 s); with an `offset` it keeps that pose relative to the marble at that moment, else it touches the marble like a platform. `contactAt` is where the marble enters along it, its middle when absent. It never sounds the hit. `anchorPiece(project, result, entityId, marbleId, time)` ties it to the marble's latest hit at or before `time`; `unanchorPiece` frees it in place.
- **`plays`:** `{kind: 'plays', marbleId, hitId, contactAt, held?, leaves?}`, a music piece (`definition.musical`, platforms only); it sounds that hit and is placed by construction. `linkPieceToHit(project, result, entityId, marbleId, hitId)` keeps the angle and takes `contactAt` from where the dot falls along the bar, so the bar only moves as far as it must to touch the marble; it refuses scenery and a hit another piece already sounds. `unlinkPiece` frees it in place and opens the hit.

`soundsHit(type, place)` decides which pieces own hits. A free rail's position is its local origin, or its entry point when a layout generates its paths, so `freePose` converts a resolved pose to a position by a layout at the world origin.

`gravity` (0.05 to 2) scales Earth's gravity everywhere, in the Rapier world, the ballistic sub-step extrapolation, the pace formula, the assists' speed thresholds. Speeds at a fixed rhythm scale linearly with gravity, so `IMPACT_SPEED`, `MIN_ARRIVAL` and `FAST_ARRIVAL` scale with it and the launch takeoff with its square root. New projects use 0.5 (`DEFAULT_GRAVITY`). `updateProject` changes it.

Schema `marble-project@6`. The app hasn't shipped, so there are no migrations: `parseProject` refuses any other version in plain words, and `scripts/convert-project-5-to-6.ts` is a one-off for local projects. A follow camera's `lead` and `smoothing` are constants the scene builder sends.

The music:

- **Songs:** imported MIDI and audio files, referenced by package-relative `path`, with the timeline time `start` they start at, and the `tempo` a MIDI file gave. A song without a `path` holds only notes, kept after the file went. A hit's time is absolute, so physics and audio never need to know about songs to place one; `songId` ties a hit imported from a song to it, and removing the song clears it.
- **Marbles:** each with a `sound`, shown in its inspector, and a list of hits. A hit has a stable ID, time, optional pitch, velocity, duration and `songId`. Hit times are absolute. `songId` ties a hit to a song; `moveSong` is the one command that changes a song's `start`, shifting its Backing and its tied hits, and the start of a marble that plays only it (`playsOnlySong`), which `marbleEdits` sees as the same run later (`isWholeRunMoved`) and leaves unsettled. `moveSongCommands` in `building/move-song.ts` keeps the rides first (`withRides`), since a later start changes the last bits a rail turns into centimeters, and takes a following length along. Dragging lands on `SONG_MOVE_STEP`, whole parking intervals of physics steps.
- **Backing:** a song's `backing`, hits of the same shape that no marble plays, and its `backingSound`, the General MIDI program they play with (absent means piano). `backingOf(project)` reads them from every song and `backingSong(project)` is where a new note goes without a song named. `upsertHits` keeps a note in the song that holds it, or in the one its `songId` names. Every note sits on exactly one marble or in Backing; hit IDs are unique across both. Hit commands address Backing with the marble ID `BACKING_ID` (`'backing'`), and so do hit selection keys (`hit:backing:<id>`). A song's selection key is `song:<id>` (`toSongKey`), and `shownSongs(project)` lists the songs that have a row. `assignHits {hitIds, marbleId}` moves hits to a marble or to Backing keeping their IDs. `assignNotesCommands(project, result, hitIds, marbleId)` in `building/assign-notes.ts` wraps it: a platform linked to a hit that leaves its marble becomes Free at its resolved pose (`freePose`), and an anchored piece is re-anchored to the marble's nearest remaining hit (`anchorHit`) with the `entryDelay` that keeps its moment, else freed. The simulation reads only marbles; Backing never has hit results.
- **Sound:** `renderMarbles(marbles, {backing})` synthesizes marbles as short strikes and each song's Backing on its own channel with each note's duration (up to 4 s, cut before the next note of the same pitch). `soundingMarbles(project)` is what the marbles play: pitched hits, less those tied to a recording. `renderProjectAudio` and the audio signature read those, every Backing and every recording at its start, so playback and the exported film soundtrack carry the same mix. Mute and Solo are `StudioCx.$mix`, view state by marble and song ID (`music/mix.ts`).

What only the film sees, such as camera rig settings, shot markers, theme and quality, sits in `film`. Detailed Blender edits stay in `scene.blend`.

**Film layers:** `project/film-layers.ts` is the table of the lists under `film` that show as layers, for what treats them alike: Edit > Undo's names, an agent's presence marks, Rename and the keys a selection may hold. Each one's row in Layers, inspector and drawing stay with it, since those really differ.

**Decor:** `film.decor` lists `{id, name, source, position, scale, rotation, snowfall?, footprint?, in?, out?, hidden?, scattered?}`. `source` is a built-in item (`decor:bauble-red`, from `blender/mm_worker/decor_catalog.json`, which the app and worker both read) or a package asset (`assets/<id>/asset.blend`); `footprint` is an asset's half size from its manifest's `fittedParams` `width` and `height`; `scattered` tags what Scatter Decor may replace. `film.madeInBlender` holds `{name, in?, out?, hidden?}` per Blender object name. Selection keys are `decor:<id>` and `blender:<name>`. What Blender reports is session state (`$blenderObjects`), never saved in the project, which `SimulationCx.$problems` reads.

`modules/scene/decor-clearance.ts` holds every marble's path, as points at most 3 mm apart with the marble's radius and time, and the pieces, in a grid per run; `decor.ts` asks it for overlaps and Move Clear, `decor-scatter.ts` for Scatter Decor. Scatter is pure and deterministic for a seed. The camera check uses `projectToFrame` with distance 0, the wall plane rather than the marble plane.

**The film's theme:** `film.theme` is `{base, parts?, glowColor?, pack?}`: `base` a built-in theme id, `parts` the look a Pack's theme gives each element type, `glowColor` its glow, and `pack` the Pack it came from with `themeId` and `themeName`. A film stores one theme, one way: its colors, wall skin and Key Light live only on `film.wall` and `film.lights`. `scene/project-themes.ts` resolves it (`resolveTheme`, `baseThemeOf`, `sceneThemeOverrides`) and owns the switches (`themeCommands`, `packThemeCommands`); each is one `updateFilm`, so one Undo restores all a switch replaced. Skins, reactions, title colors and the render look follow the base.

**Wall and Lights layers:** `film.wall` (`{color?, backgroundColor?, kind?}`, `kind` one of `plain`, `plaster`, `pegboard`, `grid`) and `film.lights` (`{key?: {color?, strength?, side?, height?, softness?, exposure?, bloom?}, added: TLight[]}`; `softness` is a share of the widest sun, 60°, `exposure` stops on top of the base theme, `bloom` 0..1; resolved by `set_scene_look` in Python and `keyLightLayer` in TS) sit on top of the applied theme. They survive a switch between built-in themes, like a piece's skin. A Pack's theme brings its own: wearing one replaces both, keeping only the Wall's `labelColor`, and leaving one clears both the same way, added lights too. A `TLight` is `{id, name, color, strength, side, height}`; `side` and `height` are shares of a quarter turn from straight in front of the wall (-1 to 1). A Pack's theme stores the same as its `wall` and `lights`; `currentLookTheme` makes one from the current look for Export This Look…. `scene/scene-layers.ts` owns the effective values (`wallLayer`, `keyLightLayer`, `addedLights`), the commands (each one `updateFilm`, so one undo step) and `sceneLayers` for the scene description. The theme defaults in `BASE_SCENES` mirror `THEMES` in `themes.py`. Selection keys: `wall`, `light:key`, `light:<id>`; neither has a timeline row.

**Groups:** `track.groups` lists `{id, name, marbleId?, pieceIds, pattern?}`: with a `pattern` a live Pattern, without one a plain Group, made with ⌘G or left by Flatten (`track/group-commands.ts`). A Pattern stores the hits it plays, in `hitIds`, and `patternSpan(marble, group)` works out its block in the timeline from them. Commands `addGroup`, `updateGroup` and `removeGroups`, which is Ungroup: the pieces stay; `removePieces` forgets the pieces and drops a Group that lost them all. The pieces are ordinary pieces; a Group is a list beside them, so nothing else reads it but the strip, Layers and the inspector.

**Patterns:** `building/patterns/` holds the contract (`contract.ts`) and `PATTERNS` (`registry.ts`). A Pattern is a pure function: arrival, hits and settings in; pieces, exit and a verdict per hit out. Each is an object in its own file (`zigzag.ts`, `staircase.ts`, `long-rail.ts`) with its label, tile drawing, what it takes (notes or silence), defaults and `fit`, so a new one is that file and a line in `PATTERNS`: the tiles, the words, the commands, the agent's `get_state.patterns` and the stored kind, a plain string, read from there. `fit-bar-pattern.ts` is what the bar Patterns share and `fit-bars.ts` and `fit-rail.ts` solve against the real simulator. `runGroupChange` adds Groups' ranges, overlaps, the release and later Groups and answers one edit. `checkPattern(project, ask, { sim })` asks the whole song and changes nothing: `verdicts`, `ending`, `refusal`, `offers`, `commands`, the only thing ever applied. It tries the way the track goes now (`along`), the other side and its own shape, up to `MAX_ATTEMPTS`, and with no Width asked a few Widths. The verdict is never stored. All of it runs in its own `pattern.worker.ts`, so Stop ends the worker and starts another; a resting pointer's check sends the ghost ahead, and a click on that tile takes its answer. `track/PatternsCx.ts` owns runs, previews and `$verdict`, `track/PatternInspector.tsx` the tiles, `studio/timeline/PatternStrip.tsx` the strip. The inspector's Bounce sets a drop per hit (`dropForBounce`) and each bar's bounce is solved: one bounce on every bar missed notes on real rhythm (54 of 58). Selection keys: `pattern:<id>` with the pieces' ids, and `range:<marble>:<from>:<to>` for a silence. `scripts/pattern-measure.ts` measures how often Patterns fit and why not (`docs/references.md`).

Edits are commands applied to an immutable document with undo and redo: `project/commands.ts` holds one Zod union, so each command has one definition with an example beside it, for agents too. `add` replaces what has the same ID, `update` changes the fields in its `patch` and deletes a field with `null`, and `remove` also takes what can't stand without it. Commands copy on write, so an unchanged section keeps its identity. Each command batch increments a revision so asynchronous work can detect intervening edits.

## Pieces

Each piece type is one definition in a registry:

- Physics shape built from its parameters
- Parameter schema with defaults and limits
- Placement rule that puts its contact surface at a trajectory point
- Default skin per theme
- Optional dynamic behavior, such as the windmill hinge with damping or motor
- Layout kind (`layout`), which decides how it is built and drawn
- Canvas colors (`palette`) and its tile in Insert (`tile`)

The first set is platform, rail, tunnel, windmill and Bowl:

- **Platform:** a box whose top face is the contact surface
- **Rail:** a smoothed path built from thin rounded segments in the marble plane. The two-wire look is visual only.
- **Tunnel:** a rail floor with a ceiling that starts shortly after the entry. Blender hides the marble inside it.
- **Windmill:** a hub that turns only around the wall normal, with angular damping or a constant-speed motor. Its angle is recorded every step and becomes rotation keyframes in Blender.
- **Rail layouts** (`piece.layout`, kind `generated`; `railLayoutInfo` in `pieces.ts`): a Rail holds one path or several, `path.points` and `path.paths` when drawn, or generated at layout time from its parameters around the point the marble enters (`generatedGeometry` in `piece-layout.ts`). Physics is the same capsule chains and the same material for all of them, one Skin, one row in Layers. `chain` (`chainGeometry`, `chainHoldTime`) is separate C's: a wall curving round through `sweep` on a radius of `arc`, `drop` apart, no stop wire. `c` is one such turn and `curve` one parabola. `gapSearch` refuses a candidate whose marble is still inside its turns at the next hit.
- **Switchback layout**: a holder for long notes built entirely from parameters. `turns` sloped legs `width` wide, stacked `drop` apart and sloping alternately left and right; each leg runs from its wall to `opening` short of the other side. Each leg is one bent wire: the wall comes down on the leg's high side, turns through a fillet of radius `bend` (default 4 cm, 0 gives a sharp corner) tangent to wall and leg, and runs down the leg. A short stop on the last leg's open side turns the marble down out of the rail. The marble rolls down a leg, falls through its opening onto the next, rolls through the bend at the wall and back, and leaves through the last opening. The hit link's angle sets the leg slope (2° to 25°) and, by its sign, the first leg's direction like a rail; `contactAt` sets where the marble enters across the top. The wall the marble moves toward at its entry rises `lip` higher to catch a sideways entry; the other wall stops at the rim. `TResolvedPiece.paths` carries the wires as polylines, one bent wire per leg from the top, then the exit stop, and `shapes` their capsules. A free Rail with generated paths has its entry point as its transform.

- **Bowl** (layout `catcher`, `simulation/pieces.ts`, `bowlGeometry` in `piece-layout.ts`): the piece that collects a marble and plays none. Its transform, or the marble's position at its anchor moment, is its mouth. One wire, a static chain of capsules, along an arc of radius `size` (6 cm) from rim to rim through the bottom, both rims curling 40° over the center, restitution 0.1. `mirror` picks the side of the marble its center lies on. `bowlCatch` says whether the marble lands in it and stays.
- **Start rail** (`building/start-rail.ts`): Build Track's free Rail at each bare marble's release, the first row under its marble in Layers (`startRailOf`), 6 cm at 10° or steeper, with a short stop past its end as a second path. The marble rolls off, meets the stop and drops almost straight, then falls 0.5 s as one released without a rail does, or down to 0.12 s when the first note comes too soon for that, so the first strike is as firm and the track's first bounces come out the same; the release moves earlier by the time the rail takes. All rails run the same way, so the marbles wait side by side and the opening frame holds them. The rail's `landingOffset` keeps how far along x the marble lands, since a marble's band of the wall lies where it lands (`frameBand`), while the marble still waits on the rail. A marble with a speed of its own gets no rail.

Rails, tunnels and windmills are scenery: anchored to the trajectory a short delay after the hit before a gap, they follow upstream edits like platforms but never sound a hit. The next platform is placed where the marble actually is, so hits stay on time whatever the gap piece does. Gap suggestions search their parameters by simulation and report honestly whether the result stays in frame and near the pace. `createSwitchbackForGap` enters where the marble has fallen 1.25 or 2.5 marble diameters below the launching hit, so the earlier path stays above the switchback; ranks leg counts (1 to 6) and slopes (2° to 17°) by an estimated hold time (`switchbackHoldTime`, rolling at 5/7 · g · sin slope from 0.35 of the entry speed and keeping the speed through the bends, within about 0.2 s rms of simulated holds at full and half gravity, with 0.6 s slack; rolling every leg from rest overestimated holds two to five times and at half gravity shortlisted only switchbacks that released the marble far too early) and the height the marble would reach at the next hit after falling from the exit; simulates the best ten per entry and width (the kit width and 0.8 and 0.65 of it) for both directions and three entry positions with a flat probe at the next hit; and scores the next dot's pace error (twice as much below the pace), frame, stray contacts and room for the next piece, then refines the best slope by ±2° and ±4°. The marble must leave early enough to fall below the switchback by the next bounce's rise plus 6 cm.

### Add a piece type

A piece type with an existing `layout` other than `path` or `tube` takes these steps. `track/piece-registry.test.ts` names the parts of steps 1 to 4 a type lacks, and `scene/skin-catalog.test.ts` and `scene/packs.test.ts` cover steps 3, 5 and 6.

1. **Definition:** add it to `pieceDefinitions` in `simulation/pieces.ts`. Insert, the tool and its key, the command palette, the Insert menu and the canvas colors read it. Pick a free letter for `tile.shortcut`, or leave it out.
2. **Icon:** add it to `pieceIcons` in `canvas/piece-icons.tsx`.
3. **Catalog:** add an element to `blender/mm_worker/skin_catalog.json` with at least three skins, and the skin each theme dresses it with. The project schema and the skin pickers read this file.
4. **Builder:** add it to the table in `build_spec` in `blender/mm_worker/skins.py`, with an existing `*_spec` function or a new one.
5. **Starter Pack:** add an item per offered skin to `packs/Starter.marblepack/pack.json`, in catalog order.
6. **Previews:** render a PNG per offered skin into `public/skins/` with `blender/tests/render_skin_previews.py`.
7. **Words:** add its name to `docs/words.md` and `src-tauri/src/modules/mcp/guides/words.md`.

Draft colors are optional: `draftPieceColors` in `scene/draft-look.ts` gives an unlisted type chrome.

The Blender worker is Python and can't read the definition, so it names some types itself. A `box` type needs nothing beyond step 4. A `rotor` type also goes in `layout` in `assets.py` and the windmill checks in `skins.py` and `contacts.py`.

A new `layout` kind, or a type drawn with the path tool, is more work: a new kind goes through `piece-layout.ts`, `shapes.ts`, `pieceOutline` and the shapes in `canvas/PieceShapes.tsx`, and a drawn type through `TPathType` in `track/keys.ts`, `pathPieceTypes` in `building/attach-edit.ts` and `pieceToolCommand` in `studio/commands.ts`.

## Simulation

Every marble has a Rapier world of its own, holding only what that marble could reach before the next parking check: nearby pieces of any marble, windmills, and the other marbles as proxies. Any enabled collider, even one that meets nothing, reshapes Rapier's broad-phase tree, and the tree's shape sets the order in which a marble's simultaneous contacts are solved, such as two rail wires; that order changes the result in the last bits and a tightly tuned run cascades from there. With one shared world a windmill 5 m from every marble broke 83 of Jingle Bells' 115 hits, and a 0.002 rad turn of a bass platform broke 36 melody hits. Separate worlds and parking keep a piece no marble comes near, and every edit on another marble that does not come near a marble, from changing its run at all. The simulation module exposes pure operations over a project document:

- `simulate` runs the world ahead of the playhead and returns samples, contacts and hit errors
- Whether a run is needed: `isSameRunInput` compares `marbles` and `track.pieces` by identity and `gravity` and `length` by value. Results key on `revision`, which every edit bumps, so on its own it would re-run a film edit. Commands copy only what they change, so an unchanged section keeps its identity; a false match would need an edit in place, which projects never get, and an equal section under a new identity only runs again. `SimulationCx` then moves the shown result to the new revision instead of asking the worker, and that is the only place a result changes revision. Whether a dot is out of frame depends on the camera, so the canvas works it out from `frameBand` and the result doesn't carry it.
- Snapshots are taken at each placed piece, so an edit re-simulates from the earliest affected snapshot
- Every piece starts parked and enters a marble's world only while that marble is within parking reach, checked every 6 steps on the global step grid: over the next 7 steps at twice the marble's speed (or a nearby marble's, when faster) plus 1 m/s and twice the tip speed of a nearby windmill, plus the fall, its radius and 5 cm. Another marble far away never widens the reach. A piece no marble reaches leaves the run bit for bit unchanged. Placed pieces enter their marble's world at once. Free and pinned static pieces stay out of the snapshot key chain; on resume `canResume` checks that every added, removed or moved static piece, old and new pose, stayed out of reach (by the fastest marble and blade tip so far) of every sample up to the snapshot, and `rebaseStaticPieces` swaps in the new records in plan order. Dragging a free piece therefore re-simulates only from the last placed piece before a marble could reach it, and the result equals a full run. Windmills are in the key chain since they always turn.
- A windmill is in the world of every marble near it; the first of those worlds drives it and the copies follow its pose each step. Parked everywhere it turns on by its motor, or slows by its damping.
- Another marble enters a marble's world as a proxy, a dynamic copy that takes the other marble's state before each step and meets only marbles, while the two could touch within two steps. The contact is solved in both worlds as between two marbles and each keeps its own marble's response. Rapier reports contacts with a proxy several steps early, so a marble contact is logged once free flight from the start of a step meets within two steps.
- `place` builds a piece for a hit dot. The contact surface is placed where the marble is at the hit time, offset by the marble radius along the surface normal. Timing is therefore correct by construction for the placed hit, and only its angle changes the future.
- `repeatPiece`, `mirrorPiece`, `autoPlace`, `continueSuggestions`, `findLongGaps`, `openLongGaps` and the gap helpers produce piece edits. They need a simulate function, so the UI calls them through the simulation worker.
- Build Track (`building/build-track.ts`): the one implementation of building a whole track, used by `AssistCx.buildTrack` and Next's answer to a gap it can't bridge (`buildOneStep`). It takes its runs and searches as deps (`TBuildTrackDeps`), the assists worker and the pool in the app (Auto place takes a `range` for its wider search) and the same request handler in this thread in Node (`localBuildDeps`). Projects are immutable, so a step's run is memoized by project and a back-up returns to an earlier project and its snapshots. `accept` judges each option against the problems the run already had (`tolerated`). `commit` gets each step as commands (`diffCommands`), which `AssistCx` folds into one undo step with `amend`. Nothing in it reads the clock or randomness: the budget for starting over counts steps, and piece IDs follow from hit IDs. While it runs `AssistCx` asks no Continue, Fix-it or Next question of its own, and `isAnswering` holds an agent's reply until every answer has landed
- Workers (`client.ts`): one simulation worker for the live run, one assists worker for Continue, the long-gap ghosts' fallback and Fix's own runs (`simulateAssist`), and a pool of assists workers (`assist-pool.ts`) for Auto place and the gap pieces, started on first use with `navigator.hardwareConcurrency − 1` workers, at most 6 (`assistPoolSize`); with fewer than 2 the assists worker answers them as before. Auto place (`prepareAutoPlace` and the `autoPlaceSearch` generator) and the gap pieces (`prepareGapSearch`, `gapSearch`) are split into stages of independent tries; the pool cuts each stage into chunks of about half a stage per worker, hands them to whichever worker is free, puts the answers back in the order the tries were asked and reduces them there, ties going to the first, so the choice is the one the single-thread `autoPlace` and `create*ForGap` make whatever the pool size or timing. The first chunk of a search to a worker carries the request (`searchTries` with `prepare`); the worker simulates the project up to the trials' end plus 0.25 s, the only part the checks read, prepares once and keeps it (`TWorkerMemory`), and later chunks carry only the tries. A gap search ends with `gapAnswer` on a worker that prepared it, for the ghost's track. One search runs at a time; a waiting request is replaced by a newer one of its kind, and `isCanceled` (Fix's Stop) ends a search between stages. Every worker posts a simulation result with each marble's samples packed into a transferred `Float64Array` (`result-transfer.ts`); cloning a song's samples as objects took about 14 ms per result.

Problems: `SimulationCx.$problems` is the one owner of the open project's problem list, read by the hit summary, Layers, the inspectors, the export sheet, the Camera track and an agent's replies. It is pending until the run matches the project and while Build Track works, and a drag keeps its last value, so neither a step nor a pointer move checks the whole run. `checkRun` in `building/export-preflight.ts` is the check itself, which Build Track, Fix and Patterns also call on their trials, whose runs are theirs by construction. `SourcesCx.$missingRecordings` feeds it the songs whose file doesn't load (`missingRecordings` in `music/audio-engine.ts`). Trials pass none, as they are about the run. A failed load is never cached, so `checkRecordings`, every 2 s while one is missing, and `TAudioEngine.prepare` find a file that came back.

Local edits (`simulation/local-edit.ts`, `ride.ts`, `studio/SimulationCx.ts`). Measured on Jingle Bells, a run of platforms is calm: 0.17° at 6 s leaves every velocity error shrinking by about 0.8 per hit and the rest of the track a rigid 6 mm away. A Rail's turns are not: a change of 6e-5 m/s entering one comes out as 0.7 m/s at the next hit, a gain of 1e3 to 1e5 that no restitution, friction or solver setting tested removes; even moving both releases 0.1 mm broke 41 hits. So translation only holds once rides are fixed:

- **Rides.** `bakeRide` stores what the run did as a `ride` on the gap piece: x, y and rolled angle per physics step relative to the entry, up to the last time the marble came within 2 mm of it before its next hit, with the exact exit state, the entry velocity and what else it touched. `followRides` puts the marble there after each `world.step`, so Rapier still reports contacts, and hands it back to physics at the last frame. A ride plays only while its `rideKey` (shape, tilt, Lands At, offset) matches, the marble enters within `rideTolerance` (0.6 m/s at Earth's gravity, scaled) and nothing outside `touches` is struck; otherwise physics runs, from where the marble is. A run with no `ride` is bit for bit what it was, so Build Track, fixtures and tuned tracks don't change: rides are made at the first edit (`withRides`), in that edit's undo step, about 30 KB for Jingle Bells.
- **Exit.** `place.leaves` keeps the velocity and spin `LEAVE_STEPS` (5) after a platform's hit, for this angle and bounce while the bounce comes out within `rideTolerance`. Spin is the reason: restoring velocity alone left 3.7 rad/s, which became 15 mm/s at the next hit and a 1.7 cm shift, enough to strike the other marble's pieces at 27 s.
- **Solve.** `settleEdit` plans pairs (`planSteps`): the first platform aims at the second's old dot, the second at its old exit, each by Newton's method on tilt and bounce from a frictionless reflection start that keeps what friction added before the edit, each try simulated only as far as its aim (about 3 ms, resumed from snapshots). A platform launching into a ride can only restore its exit; the offset goes to the first pair after the ride. Six variants skip or restore platforms first, since a platform after a gap often sits at the 0.95 bounce limit. `judge` runs each to the end; score is 100 per broken hit, 10 per new strike and 1 per mm later hits stay moved, at most 150 runs, a count so the answer is the same anywhere.
- **Hold.** A remaining break gives every piece of that marble from the first broken hit on `place.held`, the dot and velocity of the run before the edit. A held piece is placed from those, never blocked, and its hit reads `missed` for the first and `waiting` for the rest; a marble freed of one marble may break another, so `settleEdit` holds marbles in turn. `withoutBehindBreak` drops problems later than the break. `reconnect` is Fix's first try: `planSteps` reads a held piece's targets, and the marble is released once every hit plays.
- **Flow.** `SimulationCx` owns it, so an agent's edit in Film settles too. `marbleEdits` diffs the last settled project with the new one; the edit's own run waits (`isSettling`, `AssistCx.isAnswering`) until `client.settle` answers in the trajectory worker, and the changed pieces land with `amend`. Undo, redo, Revert to Opened and what Build Track and Fix land themselves (`landWorkedOut`) are left alone; a person's edit while they run settles and stops them, and a stopped Build reports the run as it then stands. A preview asks `isQuick` in the assists worker: the first variant, checked 2.5 s past the change, then `simulate` with the horizon, whose stale far part is now right. A paused preview's whole settle waits in its own line behind an edit's, and a preview's run shows under a revision no project has, so it never reads as current. A Pattern fit waits for a settle on its way (`whenSettled`) and starts from what it lands. `settleBase` keeps the run before the edit in `TWorkerMemory`, as a drag asks at every move.

Frame bands and descent pace (`placement.ts`, `pace.ts`):

- `frameBand(project, marbleId?)` with one marble is a band for building: 1.5 film frames wide at the camera's distance (`BAND_FRAMES`, `frameWidthAt`, from the lens and aspect), 0.49 m at the defaults, centered on the release. The camera pans with the run, and one frame leaves Long Rails no room in the reference's gaps. With several marbles each marble's band is 0.26 m wide (`MARBLE_HALF_WIDTH`, two zigzag columns of 9 cm bars a bar and a clearance apart), the bands sit `MARBLE_SPACING` (0.26 m) apart ordered by release x and centered on the mean release, so neighboring bands meet. Without `marbleId` it returns the band covering every marble. Open hits report `outOfFrame` against their marble's band. Where bands overlap, the other marble's pieces stand in the zigzag's way (`references.md`, Marbles side by side).
- `paceRate(project)` is (1 − e) / (1 + e) · g · T / 2 for the default platform bounce e and the median interval T of all marbles' consecutive hits up to 0.8 s, with several marbles at least `columnRate(T, g)`, clamped to 0.15 to 0.8 m/s. `columnRate` is the rate whose drop per hit d leaves `COLUMN_CLEARANCE` (6.5 cm) between a bounce's top and the piece two hits back, which a zigzag passes under: with k = g·T²/2 the bounce rises (k − d)² / 4k, so d = 3k − √(8k² − 4k · clearance). Heights at a rhythm scale with gravity but pieces do not; at half gravity and 0.5 s the default bounce left 3.5 cm and marbles struck those pieces, and the rate becomes 0.30 m/s instead of 0.26. Full gravity at 0.5 s keeps the default bounce's 0.52 m/s. `descentPace(project, hits)` anchors y*(t) = anchorY − rate · (t − anchorTime) at the earliest hit with a dot. `simulate` returns it as `TSimulationResult.pace` for the camera; `paceAt` evaluates it. `PACE_LIMIT` is 0.25 m.
- `longGapThreshold(project)` is the interval at which a bounce at the pace would rise more than `MAX_BOUNCE_RISE` (0.4 m at Earth's gravity, scaled with `gravityScale`), between 0.6 and 2 s. Rise and pace both scale with gravity, so the threshold depends on the rhythm alone, about 0.68 s for 0.5 s hits. `findLongGaps` and Auto place use it. Auto place follows a launch into a long gap for 0.3 s / √gravityScale, since the hop rises the same 7 cm at any gravity and stays in the air that much longer.

Auto place, Continue and the gap helpers treat a project with several marbles as sharing one camera. Then Auto place solves each platform's bounce from the arrival velocity and the surface normal for the takeoff that lands the next dot on the pace (`paceBounce`), corrects it once by simulation when the dot misses by more than 2 cm, and rejects candidates whose next dot ends further than `PACE_LIMIT` from y* (or further than the current dot, plus 5 cm), whose path leaves the marble's band, whose next platform would not fit inside the band, or whose marble is not falling at `IMPACT_SPEED` at the next hit. A dot below the pace recovers half its offset per hit with at least 0.75 of the pace drop; a dot above returns at once. Narrow bands leave angle windows of a degree or two (a 0.5 s flight moves the next dot about 4 cm per degree), so with several marbles the refinement and the fallback steps are 0.5°. When nothing passes, steps from −12° to 12° are tried (fast arrivals need nearly flat pieces), quarter degrees within ±3° for arrivals faster than 3 m/s, then the steps with the target 12 cm lower and higher, then −60° to 60°. The comfortable travel is two piece lengths, at most the band's half width, which centers a zigzag in a narrow band. Before a long gap the bounce gives a 1.2 m/s hop that clears the piece into the switchback. Stray contacts with another marble count only up to that marble's next open hit, beyond which its path is unbuilt free fall. An angle whose run breaks another marble's hit that was on time up to that marble's next open hit is rejected (`crossesOtherMarbles`); switchbacks, rails and tunnels for long gaps are never suggested when they touch another marble's pieces or marble. Continue drops ghosts that leave the pace, stops before a hit that starts a long gap and before a marble's last hit (whose fall past the other marbles only Auto place checks), and cuts the last ghost when a flat probe at the following hit would be blocked. A marble's path counts as unbuilt after its next open hit and after the launch into a long gap that nothing bridges yet. With one marble Auto place keeps the settling bounce that reaches the next hit at the steady speed of the default bounce, the 0.45 m frame and a soft pace.

Contacts record actual time, piece, marble and the approach `speed`: the marble's velocity toward the surface along the contact normal at the refined contact time, relative to a windmill blade's own motion. A hit is valid when its marble first touches its linked piece within 20 ms of the hit time at `IMPACT_SPEED` (0.3 m/s at Earth's gravity, scaled with `gravityScale`) or faster; a slower first contact is a resting or rolling contact and the hit is `missed` with `reason: 'resting'`. Unexpected contacts, including marble collisions, are reported separately.

## Blender bridge

The Rust host starts one Blender process per open project with the bundled worker. Requests and responses use the file mailbox proven in the desktop prototype:

- The host writes `{id, op, args}` to `.bridge/host-inbox/`
- The worker writes `{id, ok, result | error}` and progress files to `.bridge/outbox/`
- Agent tools write to a separate `.bridge/inbox/` that accepts only inspection and candidate previews
- The worker checks its inbox every 20 ms and for 2 s after a request, then every 200 ms, so an idle Blender stays quiet and a burst such as a camera drag stays quick

Operations:

| Operation        | Purpose                                                                     |
| ---------------- | --------------------------------------------------------------------------- |
| `apply_scene`    | Create or update holders, skins and keyframes from a scene description      |
| `preview_frame`  | Render an Eevee frame and an object ID pass at a time                       |
| `render_film`    | Start a film render with a preset in a separate Blender process             |
| `cancel`         | Cancel a film render job                                                    |
| `preview_render` | Start (or retarget) the background preview frames job in a separate process |
| `preview_render_cancel` | Stop the background preview frames job                               |
| `inspect`        | Report link states, detached objects and Blender-owned changes              |
| `save`, `shutdown` | Save `scene.blend` and close cleanly                                      |

Motion moves as a binary file rather than JSON. The app writes sampled positions and rotations as Float32 arrays into `.cache/motion/`, and the worker reads them with NumPy and writes F-curves with `foreach_set`. Keyframes are written at the render frame rate. Hit values become an animated custom property per piece.

Pieces in the scene description carry the resolved geometry from the simulation result (`TResolvedPiece` position, angle, `path` and `paths`), never raw transforms, so a free rail, whose transform is its local origin or the entry point of its generated paths, show where the physics put them. Each piece carries `hitTimes` (actual contact times of its linked hits), `contactTimes` (every marble contact start with it, starts within `CONTACT_MERGE` = 0.1 s of the previous one merged) and `musical` (the definition's flag).

### Themes, reactions and camera

- `TSceneDescription.theme` selects a procedural theme in `blender/mm_worker/themes.py`: `pegboard` (flat toy colors, pegboard wall, wooden pegs) and `brass` (the reference look: lavender plaster wall, brushed brass bars on bent chrome brackets with round wall bases, chrome two-wire rails, satin tunnels, brass windmills, a glass marble with a swirl core in the marble's color, one soft low sun from the upper left, a studio environment for metal reflections, AgX). Themes are data; materials are shared and created once, so Blender edits to them survive.
- The film's theme reaches the worker as its base in `theme` plus `themeOverrides` (`TSceneThemeOverrides`, the set colors of `film.wall` and `film.lights` and the theme's glow). `themes.resolve_theme` lays them over the base settings: Wall paints the wall material (named per color, so the shared base material stays untouched; Neon's grid follows the new wall), Light tints the sun, Background the world, Glow every Neon trim. `scene.apply` sets them for the apply with `themes.set_overrides`; the studio's `mm_theme` key includes them, so changing a color re-themes the untouched studio, and the skin key includes Glow only when set. The Draft Preview resolves the same theme (`draftWall`, `draftPieceColors` with the overrides); Light has no draft equivalent, and a set Background draws around the frame
- The Wall and Lights layers reach the worker as `themeOverrides` (the layers' colors on top of the theme's) and the additive `wallKind`, `keyLight` and `lights` of the scene description. `themes.set_scene_look` lays `wallKind` and `keyLight` over the settings for the apply and joins `mm_theme`'s key, so a change re-themes the untouched studio and a reset returns the theme's values. `studio.apply_lights` keeps app-owned sun objects (role `studio.light`, `mm_light_id`) in the studio collection: a light the user edited in Blender keeps its values and is hidden rather than removed when the project deletes it, so undo shows it again; an untouched one is removed. `apply_scene` reports `lights: {created, updated, skipped, removed, hidden}`. A Neon back light stays the theme's, not a layer
- Default skins are built per theme and piece type (`skins.py`). A skin root carries a fingerprint of what the app built; the app rebuilds only unedited default skins of linked holders when the theme or parameters change. Edited skins, custom skins and objects outside the MidiMarble collections are never touched. Studio objects (wall, sun, world) are re-themed only while they hold what the app last wrote.
- Reaction times: `mm_hit` of a music piece (platform) follows its `hitTimes`; scenery (rails, tunnels, windmills) never has hits, so its `mm_hit` follows `contactTimes`. Windmill blade strikes from `contactTimes` also join the contact-frame snapping of the marble. A default windmill skin flashes its whole mesh (`mm_flash` on the skin root, strength 1.2) on each contact unless Design picks `none`; `glow` sets the strength.
- Reactions: a platform's bar is a child part whose drivers read the holder's `mm_hit`: it presses along its normal and tilts a few degrees around the bracket, springing back as `mm_hit` decays. An optional emission flash uses the `mm_flash` object property. Reactions never touch holders or their keyframes. `TSceneDescription.reactions` overrides the theme values. A piece's `reaction {preset, params}` from Design overrides the theme reaction for that piece: `none` adds no drivers, `press` (`press` m, `dip` degrees), `wobble` (`angle` degrees, `frequency` Hz; a decaying swing in the wall plane whose phase comes from `mm_hit` itself, `-ln(h)·τ` being the time since the hit) and `glow` (`strength`). Drivers are simple expressions, so they run without Python auto-execution.
- Library skins (`assets.py`): a piece with `assetPath` (`assets/<id>/asset.blend`) gets the asset's `MM_ASSET` collection as its skin. The worker appends the collection once per file into a template collection outside the scene (`MM asset · <path>`, fake user, images packed) and builds skins from object copies that share the template's meshes and materials. Appending rather than linking keeps everything the scene renders inside `scene.blend`, so packages move freely and film jobs render a saved copy without library paths; a changed `asset.blend` (size or modification time) reloads the template and rebuilds its skins. Skin layout: an empty skin root under the holder (its local transform is the user's offset), an `asset frame` empty that places the asset frame on the contact surface, and the copies. Box pieces put the asset origin at the center of the top face with +Z along the contact normal, X along the length and Y into the wall; windmills put it at the hub with +Z toward the camera; rails and tunnels repeat the straight section along a curve on the top of the wire or the tunnel floor (Array and Curve modifiers). `fittedParams` from the asset's `manifest.json` scale the asset to the piece (`length`, `depth`, `thickness` per axis for boxes, `bladeLength` uniformly, `radius` across rails and tunnels), clamped to 4x. `MM_REACT_*` parts with `mm_reaction` get drivers on their delta transforms, so the modeled transform stays intact: `press` moves along the asset's -Z, `wobble` turns around the axis toward the camera, `glow` drives `mm_flash`, which the worker adds to the part's materials' emission strength. Switching between a library skin and the theme default replaces an unedited app skin and carries over the root offset; edited skins stay the user's. A missing or invalid `asset.blend` keeps an existing skin of that asset (otherwise the default is built) and is reported in `skins` as `missingAsset` or `invalidAsset`.
- Wall text (`walltext.py`): each `TSceneDescription.wallTexts` entry becomes a FONT object in `MidiMarble · managed` tagged with its title's `mm_id` and `mm_role = 'text'`: centered on its wall position, extruded by `TITLE_RELIEF` (2 mm, half each way, so the back sits on the wall), `size` as the letter size in meters, a color material, facing the camera side and turned by its wall angle. `font` names a loaded Blender font (`Bfont Regular` is built in) or a font file, which is packed. Re-applying updates a text while it still matches what the app last wrote; an edited text is skipped, and a removed edited text moves to `MidiMarble · detached`. The ID pass picks texts by their `mm_id`.
- Camera: with `TSceneDescription.camera` (from `film.camera`) the worker bakes a follow camera in `camera.py`. Follow point: the weighted center of the marbles in flight. Target: moved up to `lead` seconds ahead, smoothed with a zero-phase critically damped filter (time constant `0.04 + 0.5 * smoothing` s), so the frame follows the run's line rather than each hop and fall, and pulled along slowly where a marble nears the frame edge, faster only past 70 % of the half frame. The camera stands `distance` away at `pitch` from the wall normal, to the side of the run, so bars fan out from a point about a frame width from the center, as in the reference. Image roll stays near zero, under a degree or so. Shots set distance with eased transitions and appear as `MM · <kind>` timeline markers. Several marbles widen the distance so all stay in frame; a group always fits. Lens 30 mm (`CAMERA_LENS`, `LENS` in `camera.py`), side angle 90° from straight below the target (`SIDE_ANGLE`). The held ending: with `holdAfter` the marbles are read at the last hit and the follow point eases over a second to the middle of the last second of the run; with `holdBowl`, the mouths of the Bowls whose catch comes after the last hit (`heldBowls` in `scene-builder.ts`, only Bowls `bowlCatch` calls caught, of marbles that play last), it eases instead to half way (`BOWL_FRAME`) from the last hit's follow point to their mean, so the frame shows the last piece and the catch; `follow-camera.ts` bakes the same and `pnpm camera:check` compares them. Keyframes are baked on the studio camera, so Blender plays it without add-ons. A camera edited in Blender is taken over: `apply_scene` reports `camera: 'takenOver'` and regenerates only with `regenerateCamera`. `mode: 'manual'` leaves the camera alone.
- Contact frames: physics samples straddle each bounce and frames rarely fall on a hit, so a fast bounce would show the marble clear of its piece on every frame. The worker inserts an exact contact sample per hit (extrapolated from the incoming flight) and warps playback time locally so each hit lands on a frame of the 1/30 s grid (the frame rate's grid when it is not a multiple of 30). The shift is at most half a grid step (17 ms), and `mm_hit` uses the same snapped times so reactions start on the contact frame.
- Bowl skins (`bowl_spec` in `skins.py`) follow its wire: a wire cradle like the reference short's catcher, two chrome wires under the marble's path either side of its plane, set back so the marble rests on both, with ties every 2.5 cm and posts every 8 cm that end in a ball at the wall. Glow draws the wires as glowing tube edges on dark posts; a Bowl plays no note, so Color: By Note doesn't apply.
- Tunnels hide the marble: `mm_visible` on the marble holder is keyed 0 while the marble is fully inside a tunnel and drives the default skin's visibility.
- A Rail with several paths (`rail_paths_spec` in `skins.py`) wears the same skins as one path, following the bent physics wires point by point, and its posts end in a ball at the wall (`wall_ball`). Brass draws each wire as a pair of chrome wires either side of the marble plane, offset from the capsule line toward the side away from the marble (the outside of the bend, below the leg, outside the wall) with mitred vertex normals so the offset stays constant through the bend, with ties at the ends and wall posts at the ends and the middle of the bend. The marble side of a bent wire is the side it turns toward; a straight wire (the exit stop) faces the middle of the rail. Pegboard draws one toy rod on the capsule line with wooden pegs at the same places.
- Decor (`decor.py`): `TSceneDescription.decor` as one object per layer in `MidiMarble · managed`, `mm_role = 'decor'`, `mm_id` its selection key so the ID pass picks it; meshes are built once per item and shared, in an asset's frame (origin at the back face's center, +Z toward the camera). Asset decorations are an empty over copies of `MM_ASSET`. Timing reuses `walltext.write_timing`. Ownership follows titles: `mm_written`, a user's edit is left alone, and removing an edited one moves it to detached. `inspect` and `apply_scene` report `madeInBlender`: top-level scene objects with geometry the app doesn't own, with wall bounds. `apply_user_decor` writes their In, Out and Hidden with `keyframe_insert` on `hide_render` and `hide_viewport`, so their own animation stays, and restores what they had when the project stops setting them. `select_objects` selects by name. Their transforms are never written.
- Frame effects (`decor_effects.py`, `decor-effects.ts`, `DraftEffects.tsx`): `decor:snowfall`, catalog `effect` set, hangs from the film camera after it is baked (`attach`, from `apply_scene`). The camera travels down the wall, so a wall-fixed thing crosses the frame; only a camera child can fill it. One flat mesh at 2 cm in camera space, `BLENDED`, unlit, colored by the vertex attribute `mm_rgba`, gain `2^-exposure`: blended surfaces write no depth, so they sort over everything and take the wall's depth of field, not the blur they'd get 2 cm from the lens. A slot's `diffuse_color` stands in for Workbench. Snowfall: per-flake numbers on the mesh, one shared Geometry Nodes group places them from Scene Time alone, so any frame renders the same whatever came before; no handler, no simulation. Workbench draws outlines around every silhouette, turning soft things into rings, so Flat Light hides the snow (`flat_settings`), and the ID pass does too (`id_pass_settings`). It is seeded by the layer's ID. It has `mm_role = 'decor'` and `obj.parent` the camera, no collider, no shadow
- Bloom (`apply_bloom` in `themes.py`): `MM · bloom` compositor group, Glare type Bloom at quality Low, threshold 2.2 in scene-linear light (above any lit wall here), then an amber multiply by distance from the frame's center. Only while `bloom > 0`; a group the user made is theirs. Flat Light and the ID pass turn `use_compositing` off. Compositor math in Blender 5.4 uses the shared `ShaderNodeMath` family; `ShaderNodeMix` keeps a socket per data type, so its color sockets are by index
- The worker needs an empty start scene: a scene that already has a World keeps it (a user's edit is theirs), so the theme's fill light doesn't apply.
- Skin model: `blender/mm_worker/skin_catalog.json` lists every built-in skin per element (`platform:copper`, `rail:chrome`, `marble:glass`: ids free of themes, with label, preview, Color choices and default, reaction, variants) and each built-in theme's skin per element. The app imports the same file (`modules/scene/skin-catalog.ts`), the worker reads it (`skin_catalog.py`, bundled by `tauri.conf.json`). `resolveSkinLook` and `resolve_look` say what an element wears: its own skin or its theme's part, each property from its override, from the part only while it shows the theme's skin, or from the skin; `blender/tests/skin_look_cases.json` holds cases both test suites run. A scene description carries `themeParts` and per-marble `skin`.
- Skin builders (`skins.py`) dispatch on the skin's name, never the theme; `PieceFrame.look` is the resolved look. A platform's name picks a bar finish (`gold`, `silver`, `copper`, `dark`), a device (`device`: silver housing with a grille, a dome and end blocks in a finish, `device-copper` starting in copper, Variant another; `key`: dark housing with a white key; `knob`: dark housing with a red lens that glows on every hit unless On Hit says otherwise), or `pegboard` / `neon`. Color: Marble tints a metal skin (`tinted_metal_material`), Skin on a toy skin shows bare wood, on a glowing skin a fixed cyan. On Hit: Glow on a piece with no moving part flashes the whole skin (`flash_ready`); Glow Color swaps emission on a copy of a shared material (`glow_tinted`). Every skin keeps the collider's top face as its contact surface.
- Marble skins (`skin_materials.py`) are a sphere of the marble's radius with one material, so physics never changes with skin. Glass and Magic look into the sphere with a few samples along the view ray in the marble's space, like the parallax of codrops' Magical Marbles, instead of Eevee refraction or a volume: Glass samples twisted sheets in a blended surface, Magic three noise layers plus specks in an opaque dark orb, moved by a Value node driven by the frame. Chrome and glass reflect a small studio painted in camera space, so they look alike on every wall. Flat Light draws them in `diffuse_color`. The theme's default marble is `marble:contrast`, today's Pearl or Deep by contrast (Brass's keeps its older glass core); Pearl and Deep force a tone.
- Extra skin properties: a manifest's optional `properties` (`{name, type: number|color, default?, min?, max?}`) become rows in the Skin section, stored in `skin.properties`. `assets.apply_properties` writes each value to the material inputs and the Value or RGB nodes of that name on a per-skin copy of the material; a material without one ignores it. Deliberately simple: no driving, no parts.

### Film render

`render_film {preset, engine?, outputPath, audioPath?, samples?, jobId?}` saves a copy of the live scene to `renders/.jobs/<jobId>/scene.blend`, starts a background Blender on it with `blender/render_job.py` and answers with the job right away, so the live worker stays responsive. Presets: `draft`, 720p 30 fps, and `final`, 1080p 30 fps with Eevee, by the short side (portrait 9:16 gives 1080x1920). Draft ignores `engine` and renders with Workbench (`workbench_settings`: material viewport colors, shadows, cavity, outlines, Standard view transform, no depth of field or motion blur) and writes JPEG frames; the started and finished job report `engine: 'workbench'`. Output frame i shows time i / fps, independent of the keyframe rate. The job writes progress to `.bridge/outbox/<jobId>.progress.json`, renders PNG frames, muxes them with the soundtrack WAV into an MP4 (H.264, AAC) with FFmpeg (or with Blender's own FFmpeg through the sequencer when no binary is found) and writes the response envelope to `.bridge/outbox/<jobId>.json`. The host reads both with `blender_job_poll`. `cancel {jobId}` sets a cancel flag the job checks between frames and stops the process after a grace period. The job also stops when the app exits, and the live worker reports jobs that end without an answer. `renderFilm` in `src/modules/blender/render-film.ts` writes `renders/soundtrack.wav` from `renderProjectAudio` and follows the job. A film is always rendered inside the package; with `destinationPath`, `renderFilm` copies the finished film to the path chosen in the save panel through the host command `copy_file_out(packagePath, relativePath, destinationPath)` (absolute destination in an existing folder, copied through a temporary file and a rename) and returns that path.

Scene structure in Blender:

- `MidiMarble · managed` holds app-owned holder empties with locked transforms
- Each holder parents its skin, so Track transforms move the skin and Blender offsets stay local
- `MidiMarble · detached` receives what was changed in Blender when its piece or layer goes, hidden from renders and the viewport; untouched skins are deleted
- Everything else belongs to the user

### Background preview frames

Film shows the real look from Blender frames rendered in the background, like Final Cut's background render (`blender/mm_worker/live_preview.py`, `blender/preview_job.py`, `src/modules/film/LivePreviewCx.ts`, `live-preview.ts`). After every scene sync `DesignCx` names the applied scene with `sceneSignature` (FNV-1a over the scene description and every motion file, plus a counter for applies that change Blender without changing the description: Discard Blender Changes, Reset Camera) and `LivePreviewCx.sceneApplied` starts `preview_render {signature, fps: 30, width: 360, order, paused}`. The worker saves a copy of the scene to `.cache/preview-frames/<signature>/scene.blend` and starts a background Blender on it, like `render_film`; the same signature while the job runs only replaces its target. `blender/preview_job.py` ships in the app's resources like the worker: a test keeps every script in `blender/` in `tauri.conf.json`. Frames are every `step`-th scene frame (a 60 fps scene renders at 30 fps), named `00042.jpg`: Eevee with the film's lights, 8 samples, JPEG quality 82, 360 px wide at the film's aspect (360×640 for 9:16). A frame takes about 260 ms, on about one core at a lower priority (`NICENESS`, at most `MAX_THREADS`), so Jingle Bells fills in about 4.5 minutes of idle time.

The app owns the order. `previewFrameOrder` lists the playhead and 3 s ahead, then outward one frame ahead and one behind in turn. `LivePreviewCx.pauseForWork` runs on every press, drag, scroll, key, scrub, edit and during playback: it writes `{"order": [], "paused": true}` as `target.json` with `blender_preview_target`, without the worker's queue, and 1.5 s after the last of them writes the order from the playhead. The job re-reads it between chunks, at most about a second later. While paused it sleeps, using almost no CPU and keeping its scene and shaders. A chunk is the first missing frame of `order` and its missing neighbors, up to 4 frames, rendered as one animation render, which keeps Blender's render scene between frames. Each frame is rendered as `.partial-<frame>.jpg` and renamed, so the app never reads a half-written file. The job writes `status.json` (`state`, `pid`, `rendered`, `frameMs`) after every chunk and every 5 s while paused and exits when `order` is done. A job that failed or went silent isn't started again for that signature. `blender_preview_cancel` writes `cancel` (checked between chunks); leaving Film, turning on Draft Preview, a new signature and the worker's shutdown stop it; it also stops when the app exits. `blender_preview_frames` lists the frames and the status; the app polls it every 400 ms while the job runs.

Invalidation is the simplest correct rule: any scene change is a new signature and a new folder, so no frame of an older scene ever shows. Keeping frames before the first changed time was left out: a change at one time moves the follow camera and the marbles' paths around it, so the safe boundary needs the camera and simulation diff, not the description. Undo returns to a signature whose frames are still there; the worker keeps the newest 3 signature folders. Edits made in a Blender window reach the preview with the next scene sync. The packaged project leaves `.cache` out.

Flat Light (`workbench_settings` in `render.py`, the Draft export's) is flat lighting through the scene's own view transform and look, plus per-theme exposure offset and sheen (`themes.flat_look`, measured against Fast); metal renders darker (`FLAT_METAL`) and Neon's glowing materials brighter (`FLAT_NEON`) as it has neither reflections nor emission. `pnpm blender:preview` compares the wall per theme (`check_flat_colors.py`).

`FilmView` draws in the app while playing and while paused when Blender's still is not at the playhead but a frame is: the Draft Preview with `LivePreviewFrame` over it and `SelectionOverlay` above that, a canvas that follows `$playhead` outside React, draws the nearest frame within one frame once decoded (`PreviewImageCache`, 150 images, least recently used out, decoding 1 s ahead), keeps the last frame 0.25 s while the next decodes and fades over 140 ms to the Draft Preview where nothing is rendered. The ruler's render bar draws `renderedSpans`. A camera drag in the preview (`camera-orbit.ts`) sets `FilmCx.$orbit`: the Draft Preview bakes the camera again with those angles on each move, about 14 ms for Jingle Bells, with no history, simulation or sync. Release makes the one edit, and the Draft Preview holds until Blender's still of the new angle is there.

## Agents

Agents connect over MCP only (see MCP below). The person's own Claude Code, Codex or Claude app starts `midimarble mcp`, which talks to the open app, so an agent has the same commands a person has. Every edit is one named Undo step, shown live; the Agent menu and the notice show who is connected and what is running, and Stop ends a running Build Track, Fix or export.

The package's `agent/` folder (`agents/folder.rs`) holds what the project wants from agents: `AGENTS.md`, `references/` (`set_references`), `notes/`, `scratch/`, and `runs/`, which logs each MCP session. New skins and decor come in with `add_asset`, and `preview_frame` renders a still for the agent.

## Marble skins

A marble's `skin` reaches the worker through the scene description as a piece's does. A built-in id resolves in `skin_catalog.resolve_look`; a library item comes with `assetPath`, and `scene.ensure_skin` then builds it as `assets.create_asset_skin` does for a piece, with the `sphere` layout: origin at the marble's center, even scale from `fittedParams.radius`, the tunnel visibility driver on each model. `blender:design` checks this from the command on (`scripts/export-marble-skin-scenes.ts`, `blender/tests/check_marble_look.py`), reading the materials and the rendered pixels. The default skin, `marble:contrast`, is pearl or deep by contrast; a deep body is as light as it can be and keep 3:1, between `DEEP_LUMINANCE` 0.05 and 0.09.

Camera **Turn** (`film.camera.turn`, radians, absent is 90°) is the view's side angle around the target. **Sway** (`film.camera.sway`, absent is 1) scales how it follows the run and its own roll in `camera.view_turn` and `viewTurn`. Wall kind **plain** is a flat material with no texture.

## MCP

`midimarble mcp` is the app binary as a local stdio MCP server (`src-tauri/src/modules/mcp`). `main.rs` branches before Tauri starts, so there is no window and no second app. JSON-RPC is hand-written (`protocol.rs`) with newline-delimited messages; stdout carries only protocol. The process answers `initialize`, `tools/list` and `get_guide` itself (guides are markdown in `mcp/guides/`, built into the binary) and sends every other tool, one connection per call, over a Unix socket to the running app.

- **Socket:** `~/Library/Caches/MidiMarble/mcp-<binary>[-debug].sock`, computed from the binary's own name in both processes, so a bundled app and a debug build don't meet. The folder is 0700 and the socket 0600; there is no network port. A live socket is left alone and a stale one replaced. `MM_MCP_SOCKET` overrides the path for tests. With no socket the server answers that the app isn't open or Enable MCP is off.
- **Enable MCP** (Agent menu and Help menu, `mcp.json` in the support folder) is on by default: the socket exists only while the app is open and only this user can reach it, and every edit shows in the window with Undo, so connecting needs no setup step. Turning it off removes the socket.
- **Bridge:** a connection thread emits `McpRequestEvent` to the front end and waits on `mcp_respond`. `McpCx` runs calls one at a time through `runTool` (`src/modules/mcp/mcp-tools.ts`). `imagePath` blocks become base64 image blocks in the host. The host appends each call to `agent/runs/mcp-<session>.jsonl`, the benchmark record.
- **Edits:** `StudioCx.runAgentStep` folds everything a call does into one undo group named "Agent: …", shown in a notice with Undo and in Edit > Undo; notices raised meanwhile become the reply. Each reply waits for the run to match the project (at most 8 s) and carries the hit summary and problems from `SimulationCx.$problems`, the window's model. A pointer held down, an open alert or the Import Song sheet makes an edit wait 2 s, then say busy.
- **Tools** stay these ten; a new command needs no new tool. `project.execute` takes project commands plus `placePiece`, `applySkin`, `placeDecor` and `scatterDecor`, which expand in `project-commands.ts`. Commands that ask through a panel take `args.path` instead (`ARGUMENT_COMMANDS`) or say which tool replaces them.
- **`preview_frame`** always renders through Blender's `preview_frame`, draft at 540 wide and blender at 1280. The Draft Preview can't be captured: it is a canvas with SVG and DOM above it, and only exists in Film.
- **Connect** (`connect.rs`, `McpCx.toggleConnection`, words in `mcp/agent-connect.ts`): `mcp_connect` finds `claude` or `codex` in a fixed list of install locations, then the Claude desktop app's newest bundled copy, then the login shell, as a GUI app's PATH reaches none of them. It runs the tool's `mcp remove` (failure ignored) and `mcp add … -- <binary> mcp` on a background thread with stdin closed and 20 s for both, where `<binary>` is `current_exe`. With no tool found it copies the command text with the plain name, through `pbcopy`, since a native menu item has no user gesture for the web clipboard. `mcp_connections` reads `~/.claude.json` and `~/.codex/config.toml` read-only and compares the listed command with this binary; only the tools write those files. `McpCx` turns on Enable MCP after a Connect. An agent can't run these commands (`PERSON_COMMANDS` in `mcp-tools.ts`).
- **Rules for agents** travel in `initialize`'s `instructions` (`protocol.rs`), as no folder holds an `AGENTS.md`: `get_guide` first, own files in the project's `agent/` folder, the film only through the tools.

**What `run_command` answers.** Every reply says `changed`, whether the call made an Undo step, and `edit.undo` and `edit.redo` name what they took back in `undid` and `redid`. `project.execute` checks each command strictly (`commandProblem` in `mcp/project-commands.ts`): an unknown field is an error that shows the command's shape, a patch is checked against its record, and commands that leave the project as it was answer `changed: false` with no Undo step. `args.select` refuses a key the project doesn't know; `edit.select` selects and does nothing else. `build.track` answers when done, or at once with `wait: false`, and `build.rebuildFrom` answers when done (region-local in `ARGUMENT_COMMANDS`: it runs the same `AssistCx.buildTrack` from `rebuildTarget`); meanwhile `get_state.building` gives progress and `get_state.lastBuild` the result. `get_state` and `build.stop` are answered outside the front end's queue, so they work during a long call on another connection, and other edits answer that Build Track is running. An agent's `build.next` places a gap piece in the same call instead of showing a ghost, and `settled` waits for `AssistCx.isAnswering`, so the reply and the next call see the finished step.

**Who is connected.** Once a client has initialized, the stdio process holds one more socket connection open for its whole life, sending one `__presence` line with its session and clientInfo name (`keep_presence`, retrying every 2 s while the app is away). `tools/call` can't reach that name, since it forwards only listed tools. The host keeps these by session (`ConnectedClients`) and emits `McpClientsEvent` when one joins or hangs up; `mcp_status` has the same list. Turning Enable MCP off hangs up on them, and they come back when it's on. `agentStatusLine` (`mcp/agent-presence.ts`) words it, with product names for known clients.

**An agent in the window.** `McpCx.answer` wraps each queued call: `presenceLabel` says what it is doing (null for a read), `AgentPresenceCx.begin` raises the notice's agent line for the call's life plus 1.5 s, and `runProjectCommands` refines it from its commands ("Placing Platform 12"). A `build.track` with `wait: false` holds the line until the build ends. `$current` changes only when a call starts, ends or relabels. `McpCx.stop` (Stop) bumps `stopEpoch`, stops a Build Track or Fix if the call is in an agent step (a person's own build is theirs) and cancels an export the call started. A call sees the epoch change: one still waiting for its run doesn't edit, a queued one is refused, and each reply says the person pressed Stop. Calls arriving within 1.5 s are refused too, since they were sent before the agent could know.

**What an edit touched.** `McpCx.watchEdits` diffs each history change made inside an agent step (`touchedKeys`, selection keys of changed marbles, pieces and titles, Wall, lights, Decor, shots, Camera and Song) into `$touched`, entries lasting 1 s. `AgentTouched` in `TrackCanvas.tsx` and `AgentTouchedOverlay` in `DraftPreview.tsx` draw the selection's outline with a CSS fade (no fade under Reduce Motion); the film one follows `$frame` only while something is marked. Sidebar sets `data-agent-touched` on the rows directly, so the list doesn't render.

**`get_state.selection`** is resolved (`resolveSelection` in `mcp/mcp-state.ts`): a hit with its marble, time, note, status, dot and platform (id, place, angle, length); a piece with its place, angle, length, params and hit; marbles, titles, lights, decor, shots and other layers with what identifies them. Every item has a `key` for `args.select`. Edit replies still give `selection` as keys. `get_state` also passes `building` and `lastBuild`.

**Project commands check against the project** (`mcp/project-commands.ts`): shape first, then ids and values (`valueProblem`): a skin must exist and fit its element, a theme must exist, ids must be there, a title's font must be usable. `updateFilm` merges into `camera`, `wall` and `lights`, and an update into a skin and a marble's `start`, so an agent names only what changes. An error names the field that is wrong and shows that field's shape. `list_commands` answers with `skins`; `get_state` holds the camera, each marble's color, radius and skin, what the wall and Key Light show with `own` on top of the theme, titles and Pack themes. A Pack theme's id works in `updateFilm`, which copies it in as the Theme picker does.

`project.execute` also takes `{ type: 'applyPattern', marbleId, from, to, kind, width, bounce, maxTilt, dryRun }`, alone in its call since it fits against the real run, and `{ type: 'flattenPattern', groupId }`. Editing how a live Pattern's piece stands is refused in words; its skin and Depth aren't. It goes through `checkPattern`, as a person's click does, so it refuses the same way. `dryRun` changes nothing and answers what applying would: `fits`, `verdicts`, `refusal`, `ending`, `offers`, `problems` and `measures`: hits on time, column straightness, drop per hit, median tilt. `get_state.patterns` lists the kinds.


The package is registered as a macOS document package so Finder shows it as one file. Every stored path is package-relative. Added Packs live in the app's support folder with the same item layout; there is no global library.

Library item:

```txt
<item-id>/
├── manifest.json  # versjon `marble-asset@<n>`: role, piece type, parameters, contact surface, reactions
```

The `agent/` folder is created on first agent use. References are the images and `references.md` in `agent/references/`; `set_references` replaces them; the window has no panel for them. Films and Packs leave `agent/` out.

### Packs

A Pack is a `.marblepack` folder: `pack.json` (`marble-pack@1`: id, name, version, optional description, author and link, and the items), `themes/<id>.json`, `assets/<id>/` as library items, optional `picture.png`. Packs hold themes, skins and decor only, nothing with a hitbox. `pack.rs` validates ids and refuses symlinks.

Only the Starter Pack is there by default. Packs… lists the Packs in the app bundle (`packs/`, resources: Starter and Christmas) and any file through Import from File…. Adding copies the Pack to `Packs/` in the app's support folder, for every project on this Mac, and changes nothing in the open project. `addedPacks` in `library-client.ts` is the list Insert, the tiles and the Theme picker read; `addedBuiltInDecor()` gives a bundled Pack's `source` items, built-in procedural decor ids that have no asset until real ones exist.

Only what a project uses is copied into it, as an ordinary library item or the film's theme. Each copy records its origin `{ packId, packName, version, author?, link? }` (`SPackOrigin`), so a project on another Mac still names the Pack: the line reads "Christmas Pack · Not Added" and opens that Pack's card. Items keep rendering either way. `version` changes nothing yet; it is kept so updates can be told apart later.

## Menu bar

The host builds the macOS menu bar (`src-tauri/src/app/menu.rs`). Before the web view loads it shows the app menu, AppKit's Edit items and Window. Once mounted, the front end (`src/modules/studio/native-menu.ts`) sends the menus laid out from the command registry with `menu_set_bar` (again when Recent changes) and later changes of titles, enabled and checked states with `menu_update_items`, diffed and batched. Choosing a command item emits `menu-command-event` with its id (`file.save`, `help.quickHelp#help` for a second item of a command, `recent:<path>`, `recent.clear`); the front end runs the command through the registry. Cut, Copy, Paste and the app and Window menus are AppKit's predefined items and never reach the front end. Save As… copies a package with `copy_project` (everything but `.bridge/`), Clear Menu calls `clear_recent_projects`. The `exports_typescript_bindings` Rust test writes the specta bindings without starting the app (`MM_BINDINGS_OUT=<path> cargo test exports_typescript_bindings`).

## Testing

- **`pnpm test`:** unit tests with Vitest, under a minute. No whole songs: each on a small project of a few hits.
- **`pnpm test:e2e`:** `*.e2e.test.ts`, with the Jingle Bells build, the fixture checks and the performance tests. It takes minutes.
- **Blender:** `camera:check` compares the follow camera with its port. `blender:check`, `blender:design`, `blender:film` and `blender:preview` build scenes headless, read the keyframes back and render.
- **UI:** the UI development surface runs in a browser with a mocked host. Native checks use a bundled debug build (`pnpm exec tauri build --debug --bundles app`).
