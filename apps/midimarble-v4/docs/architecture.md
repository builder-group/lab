# Architecture

This document describes how MidiMarble v4 is built. The product behavior is in [ux.md](ux.md) and the target films are in [references.md](references.md). Earlier prototypes in `apps/.local/midimarble-desktop`, `apps/.local/midimarble-blender`, `apps/midimarble` and `apps/_deprecated/midimarble` are references, not sources of truth.

## Stack

- **Host:** Tauri 2 on macOS, started from the community `desktop-tauri` template. The Rust host owns files, packages and processes: Blender, FFmpeg and the agent CLIs.
- **UI:** React, TanStack Router and Tailwind, structured by the community [React project structure](https://github.com/builder-group/community/blob/develop/docs/conventions/project-structure-react.md). The Rust side follows the [Rust project structure](https://github.com/builder-group/community/blob/develop/docs/conventions/project-structure-rust.md).
- **State:** `feature-state` atoms and `Cx` owners following the lab rules
- **Compose view:** Three.js
- **Physics:** Rapier's deterministic WASM build (`@dimforge/rapier3d-deterministic-compat`) in a Web Worker. The same simulation module runs headless in Node for tests and fixtures.
- **Documents:** JSON validated with Zod and versioned with [`versjon`](https://www.npmjs.com/package/versjon), so the format can change through migrations
- **Blender:** a bundled Python worker started as a dedicated Blender process. The app never installs a Blender add-on or changes Blender preferences.

Tauri suits the job: the host needs process control and file packages, and Blender does the final rendering, so a bundled Chromium would add weight without benefit.

## Units and time

Distances are metres and angles are radians, matching Blender. New projects use a kit 1.5 times the Marble Race Kit (`KIT_SCALE` in `simulation/pieces.ts`): 24 mm marbles (`DEFAULT_MARBLE_RADIUS`), 9 cm × 1.2 cm × 4.5 cm platforms and every other piece default scaled alike, with the camera at 0.85 m, which reads at the reference film's size. Saved projects keep their explicit parameters and marble radius. Time is seconds on one shared timeline. Physics runs at a fixed 240 Hz; render frame rates are derived from it at export.

## Data model

The project document is component based. An entity is a stable ID with a set of typed components. Behavior lives in plain modules that read components, the way systems do in an ECS; there is no ECS runtime framework.

Components:

| Component   | Data                                                              |
| ----------- | ----------------------------------------------------------------- |
| `marble`    | Radius, color, lane ID                                            |
| `release`   | Wall position and timeline time                                   |
| `piece`     | Piece type and its physical parameters                            |
| `transform` | Wall position and angle                                           |
| `hitLink`   | Lane and hit ID, angle, contact position, pin; `anchored` and `offset` for anchors |
| `skin`      | Asset ID (optional), link state and property overrides: `colour`, `onHit`, `glowColor`, `variant`, `properties`; on pieces and marbles |
| `reaction`  | Reaction preset and parameters of older projects; `skin.onHit` wins and replaces it when set |
| `wallText`  | Text, font, size, depth and wall position                         |

A platform is an entity with `piece`, `hitLink` and `skin`. New features add components rather than new entity classes. Decor is the exception that proves it: it has no physics, so it isn't an entity the simulation could read, and lives in `design.decor`.

A piece is in one of three states, and `simulation/attach.ts` converts between them while keeping its world pose (each helper returns `{entity, commands}` with one `upsertEntity` command):

- **Free:** a `transform` and no `hitLink`. Environment the marbles may strike.
- **Anchored:** a `hitLink` with `anchored: true` (scenery types are always anchored). The piece enters the run at the hit time plus its `entryDelay` (up to `ANCHOR_DELAY`, 10 s); with an `offset` it keeps that pose relative to the marble at that moment, else it touches the marble like a linked piece. It never sounds the hit. `anchorPiece(project, result, entityId, laneId, time)` anchors to the latest hit of the lane at or before `time`; `unanchorPiece` frees it in place.
- **Linked:** a music piece (`definition.musical`, platforms only) with a plain `hitLink`; it sounds that hit and is placed by construction. `linkPieceToHit(project, result, entityId, laneId, hitId)` keeps the angle and takes `contactAt` from where the dot falls along the bar, so the bar only moves as far as it must to touch the marble; it refuses scenery and a hit another piece already sounds. `unlinkPiece` frees it in place and opens the hit.

`soundsHit(type, hitLink)` decides which pieces own hits. A free rail or switchback's transform is its local origin or entry point, so `freePose` converts a resolved pose to a transform by a layout at the world origin.

Physics settings sit in `physics`: `gravityScale` (0.05 to 2) scales Earth's gravity everywhere, in the Rapier world, the ballistic sub-step extrapolation, the pace formula, the assists' speed thresholds and loop entry. Speeds at a fixed rhythm scale linearly with gravity, so `IMPACT_SPEED`, `MIN_ARRIVAL` and `FAST_ARRIVAL` scale with it and the launch takeoff with its square root. New projects use 0.5 (`DEFAULT_GRAVITY_SCALE`); the `marble-project@3` migration sets 1 for older projects, so they play exactly as before. The `setPhysics` command changes it.

Schema `marble-project@3` (migration from `@2`): adds `physics`, and turns scenery that `@2` linked to a hit (windmills, rails, tunnels and switchbacks at or before their hit) into anchors on the lane's previous hit with the delay that keeps their moment, so the hit they used becomes open. Scenery already after its hit keeps its link, which now anchors it.

Schema `marble-project@4` (migration from `@3`): adds `music.backing`, the notes no marble plays, and an optional `duration` on every hit, the note's MIDI length. Migrated projects start with an empty Backing, since older imports dropped those notes. `design.themeOptions` (`{ colorByNote? }`, all optional) needs no migration. Neither do `design.themes`, the optional list of project themes (below), or `design.wall` and `design.lights`, the Film layers' changes on top of the theme (below).

Music is stored beside the entities:

- **Sources:** imported MIDI and audio files, referenced by package-relative path
- **Lanes:** one per marble, with an instrument (shown as its Part's Sound on the Song, never on the marble) and a list of hits. A hit has a stable ID, time, optional pitch, velocity and duration.
- **Backing:** `music.backing`, hits of the same shape that no marble plays, and `music.backingInstrument`, the General MIDI program they play with (absent means piano). Every note sits in exactly one lane or in Backing; hit IDs are unique across both. Hit commands address Backing with the lane ID `BACKING_ID` (`'backing'`), and so do hit selection keys (`hit:backing:<id>`). `assignHits {hitIds, laneId}` moves hits to a lane or to Backing keeping their IDs. `assignNotesCommands(project, result, hitIds, laneId)` in `music/assign-notes.ts` wraps it: a platform linked to a hit that leaves its lane becomes Free at its resolved pose (`freePose`), and an anchored piece is re-anchored to the lane's nearest remaining hit (`anchorHit`) with the `entryDelay` that keeps its moment, else freed. The simulation reads only lanes; Backing never has hit results.
- **Sound:** `renderLanes(lanes, {backing})` synthesizes marble lanes as short strikes and Backing on the next free channel with each note's duration (up to 4 s, cut before the next note of the same pitch). `renderProjectAudio` and the audio signature include Backing, so playback and the exported film soundtrack carry it; a recording still plays alone.

Design-only state, such as camera rig settings, shot markers, theme, render preset and loop flag, sits in a `design` section. Detailed Blender edits stay in `scene.blend`.

**Decor:** `design.decor` (optional, so `marble-project@4` files without it stay valid, no bump) lists `{id, name, source, position, scale, rotation, depth, text?, snowfall?, garland?, footprint?, in?, out?, hidden?, scattered?}`. `source` is a built-in item (`decor:bauble-red`, from `blender/mm_worker/decor_catalog.json`, which the app and worker both read) or a package asset (`assets/<id>/asset.blend`); `footprint` is an asset's half size from its manifest's `fittedParams` `width` and `height`; `scattered` tags what Scatter Decor may replace. `design.madeInBlender` holds `{name, in?, out?, hidden?}` per Blender object name. Selection keys are `decor:<id>` and `blender:<name>`. What Blender reports is session state (`$blenderObjects`), never saved in the project, which `preflightExport` reads by default.

`modules/design/decor-clearance.ts` holds every marble's path, as points at most 3 mm apart with the marble's radius and time, and the pieces, in a grid per run; `decor.ts` asks it for overlaps and Move Clear, `decor-scatter.ts` for Scatter Decor. Scatter is pure and deterministic for a seed. The camera check uses `projectToFrame` with distance 0, the wall plane rather than the marble plane.

**Project themes:** `design.themes` (optional, so `marble-project@4` files without it stay valid) holds themes the project made: `{id, name, base, overrides, origin?}`. `base` is a built-in theme id; `overrides` holds the few designer-facing colours as `#rrggbb` display sRGB (`wallColor`, `lightColor`, `glowColor`, `backgroundColor`), absent ones keeping the base's look; `origin: 'agent'` marks one an agent made. `design.theme` names a built-in id or a project theme's id. `design/project-themes.ts` resolves it (`resolveTheme`, `baseThemeOf`, `sceneThemeOverrides`) and owns the theme edits (Duplicate Theme, rename, delete with fallback to the base, overrides, agent themes); each is one `setDesign` batch, so undo works like any edit. Skins, reactions, title colours and the render look follow the base.

**Wall and Lights layers:** `design.wall` (`{color?, backgroundColor?, kind?}`, `kind` one of `plaster`, `pegboard`, `grid` (an old file's `tinsel` reads as `plaster` and its `band` goes, `withoutRemovedFields`); `band` one of `full`, `left`, `right`, where a Tinsel wall shows, also `wallBand` on a project theme and in the scene description) and `design.lights` (`{key?: {color?, strength?, side?, height?, softness?, exposure?, bloom?}, added?: TLight[]}`; `softness` is a share of the widest sun, 60°, `exposure` stops on top of the base theme, `bloom` 0..1; added later, no bump, and resolved by `set_scene_look` in Python and `keyLightLayer` in TS) are the project's changes on top of the applied theme, on any theme, and survive a theme switch like a piece's skin. A `TLight` is `{id, name, color, strength, side, height}`; `side` and `height` are shares of a quarter turn from straight in front of the wall (-1 to 1). A project theme stores the same as `overrides` colours plus `wallKind`, `keyLight` and `lights`: `duplicateThemeCommands` of the applied theme moves the project's changes into the copy and clears them, as one edit. `design/scene-layers.ts` owns the effective values (`wallLayer`, `keyLightLayer`, `addedLights`), the commands (each one `setDesign`, so one undo step) and `sceneLayers` for the scene description. The theme defaults in `BASE_SCENES` mirror `THEMES` in `themes.py`. Selection keys: `wall`, `light:key`, `light:<id>`; neither has a timeline row.

Edits are commands applied to an immutable document with undo and redo. Each command batch increments a revision so asynchronous work can detect intervening edits. Content fingerprints separate music, track and design so a design change never invalidates motion.

## Pieces

Each piece type is one definition in a registry:

- Physics shape built from its parameters
- Parameter schema with defaults and limits
- Placement rule that puts its contact surface at a trajectory point
- Default skin per theme
- Optional dynamic behavior, such as the windmill hinge with damping or motor

The first set is platform, rail, tunnel, windmill and switchback:

- **Platform:** a box whose top face is the contact surface
- **Rail:** a smoothed path built from thin rounded segments in the marble plane. The two-wire look is visual only.
- **Tunnel:** a rail floor with a ceiling that starts shortly after the entry. Blender hides the marble inside it.
- **Windmill:** a hub that turns only around the wall normal, with angular damping or a constant-speed motor. Its angle is recorded every step and becomes rotation keyframes in Blender.
- **Switchback** (layout `holder`): a holder for long notes built entirely from parameters. `legs` sloped legs `width` wide, stacked `drop` apart and sloping alternately left and right; each leg runs from its wall to `opening` short of the other side. Each leg is one bent wire: the wall comes down on the leg's high side, turns through a fillet of radius `bend` (default 4 cm, 0 gives the old sharp corner) tangent to wall and leg, and runs down the leg. A short stop on the last leg's open side turns the marble down out of the switchback. The marble rolls down a leg, falls through its opening onto the next, rolls through the bend at the wall and back, and leaves through the last opening. The hit link's angle sets the leg slope (2° to 25°) and, by its sign, the first leg's direction like a rail; `contactAt` sets where the marble enters across the top. The wall the marble moves toward at its entry rises `lip` higher to catch a sideways entry; the other wall stops at the rim. `TResolvedPiece.paths` carries the wires as polylines, one bent wire per leg from the top, then the exit stop, and `shapes` their capsules. A free switchback's transform is its entry point. A switchback was chosen over a half-pipe: a U-rail can only release the marble over its lower lip on the first swing, since the marble has less energy on every later one, so a U as wide as a lane holds for one swing or traps the marble for good. The switchback's hold time grows with its legs, and its wall bumps shed the speed gained on each leg. The half-pipe was reasoned about, not simulated.

- **Finish** (layout `catcher`, `simulation/pieces.ts`, `finishGeometry` in `piece-layout.ts`): the piece that catches a marble after its last note and plays none. Its transform, or the marble's position at its anchor moment, is its mouth. `style` 0 is a Chute: one wire (a static chain of capsules, like a switchback's) along an arc of radius `size` (6 cm) around a centre just below and beside the mouth, from a backstop that curls 15° over the centre on the `mirror` side (+x at 0) down to where it slopes 20°, then straight on for `length` (19.5 cm) as the run-out, and a cover wire over the run-out from 0.8 arc radii past the curve, flared up at its start, 2 marble radii, 2 wire radii and 6 mm above it, so a marble that lands at speed and leaves the curve flying is led down the run-out instead of over it (without it, arrivals above 3 m/s flew off). `style` 1 is a Cup: the arc from rim to rim through the bottom, both rims curling 40° over the centre, with the mouth a quarter radius up and toward the backstop side. Restitution 0.1, friction 0.4. `TResolvedPiece.paths` carries the wire, then the cover. `finishCatch(result, entityId)` (`simulation/finish.ts`) reads the run: the marble's first contact must be on the inside of the wire and, for a Chute, at least 3 cm from the run-out's end; from then the marble must stay inside the catch curve or within a marble diameter of the wire until it rolls off the Chute's end (after rolling 3 cm along it) or the run ends: `caught`, else `escaped`; `missed` without such a contact, `blocked` when the earlier run passes through it. Dropped from rest above the mouth at half gravity a Chute catches every arrival from 1 to 5 m/s straight down or moving up to 1 m/s toward the backstop, and at Earth's gravity; a Cup up to 4 m/s and 0.6 m/s sideways (faster, the marble swirls up and out of its mouth). `compose/finish-assist.ts` holds Add Finish (`findFinish`: anchors a Finish to the lane's last hit at the first falling sample 7, 10, 13, 17, 22, 28 or 35 cm below the hit's dot within 1.2 s, backstop toward the marble's travel first; simulates past the project end when needed and keeps the first try that `finishCatch` calls caught, breaks no hit that played, no other marble touches and leaves the marble off other lanes' pieces), Place Finish Again (`finishFix`) and `withFinishes` for fixture builds. `asLaneFinish` (`step-loop.ts`) keeps one Finish per marble when a tool click or a drop adds one.

Switchbacks, rails, tunnels and windmills are scenery: anchored to the trajectory a short delay after the hit before a gap, they follow upstream edits like platforms but never sound a hit. The next platform is placed where the marble actually is, so hits stay on time whatever the gap piece does. Gap suggestions search their parameters by simulation and report honestly whether the result stays in frame and near the pace. `createSwitchbackForGap` enters where the marble has fallen 1.25 or 2.5 marble diameters below the launching hit, so the earlier path stays above the switchback; ranks leg counts (1 to 6) and slopes (2° to 17°) by an estimated hold time (`switchbackHoldTime`, rolling at 5/7 · g · sin slope from 0.35 of the entry speed and keeping the speed through the bends, within about 0.2 s rms of simulated holds at full and half gravity, with 0.6 s slack; rolling every leg from rest overestimated holds two to five times and at half gravity shortlisted only switchbacks that released the marble far too early) and the height the marble would reach at the next hit after falling from the exit; simulates the best ten per entry and width (the kit width and 0.8 and 0.65 of it) for both directions and three entry positions with a flat probe at the next hit; and scores the next dot's pace error (twice as much below the pace), frame, stray contacts and room for the next piece, then refines the best slope by ±2° and ±4°. The marble must leave early enough to fall below the switchback by the next bounce's rise plus 6 cm.

## Simulation

Every marble has a Rapier world of its own, holding only what that marble could reach before the next parking check: nearby pieces of any lane, windmills, and the other marbles as proxies. Any enabled collider, even one that meets nothing, reshapes Rapier's broad-phase tree, and the tree's shape sets the order in which a marble's simultaneous contacts are solved, such as two switchback wires; that order changes the result in the last bits and a tightly tuned run cascades from there. With one shared world a windmill 5 m from every marble broke 83 of Jingle Bells' 115 hits, and a 0.002 rad turn of a bass platform broke 36 melody hits. Separate worlds and parking keep a piece no marble comes near, and every edit in another lane that does not come near a marble, from changing its run at all. The simulation module exposes pure operations over a project document:

- `simulate` runs the world ahead of the playhead and returns samples, contacts and hit errors
- Snapshots are taken at each placed piece, so an edit re-simulates from the earliest affected snapshot
- Every piece starts parked and enters a marble's world only while that marble is within parking reach, checked every 6 steps on the global step grid: over the next 7 steps at twice the marble's speed (or a nearby marble's, when faster) plus 1 m/s and twice the tip speed of a nearby windmill, plus the fall, its radius and 5 cm. Another marble far away never widens the reach, and a lone marble's runs match the earlier shared world bit for bit. A piece no marble reaches leaves the run bit for bit unchanged. Placed pieces enter their marble's world at once. Free and pinned static pieces stay out of the snapshot key chain; on resume `canResume` checks that every added, removed or moved static piece, old and new pose, stayed out of reach (by the fastest marble and blade tip so far) of every sample up to the snapshot, and `rebaseStaticPieces` swaps in the new records in plan order. Dragging a free piece therefore re-simulates only from the last placed piece before a marble could reach it, and the result equals a full run. Windmills are in the key chain since they always turn.
- A windmill is in the world of every marble near it; the first of those worlds drives it and the copies follow its pose each step. Parked everywhere it turns on by its motor, or slows by its damping.
- Another marble enters a marble's world as a proxy, a dynamic copy that takes the other marble's state before each step and meets only marbles, while the two could touch within two steps. The contact is solved in both worlds as between two marbles and each keeps its own marble's response. Rapier reports contacts with a proxy several steps early, so a marble contact is logged once free flight from the start of a step meets within two steps.
- `place` builds a piece for a hit dot. The contact surface is placed where the marble is at the hit time, offset by the marble radius along the surface normal. Timing is therefore correct by construction for the placed hit, and only its angle changes the future.
- `repeatPiece`, `mirrorPiece`, `autoPlace`, `continueSuggestions`, `findLongGaps`, `openLongGaps` and the gap helpers produce piece edits. They need a simulate function, so the UI calls them through the simulation worker.
- Build Track (`compose/build-track.ts`): the one implementation of building a whole track, used by `AssistCx.buildTrack`, Next's answer to a gap it can't bridge (`buildOneStep`) and `scripts/build-jingle-fixture.ts`. It takes its runs and searches as deps (`TBuildTrackDeps`), the assists worker and the pool in the app (Auto place takes a `range` for its wider search) and the same request handler in this thread in Node (`localBuildDeps`). Projects are immutable, so a step's run is memoised by project and a back-up returns to an earlier project and its snapshots. `accept` judges each option against the problems the run already had (`tolerated`). `commit` gets each step as commands (`diffCommands`), which `AssistCx` folds into one undo step with `amend`. Nothing in it reads the clock or randomness: the budget for starting over counts steps, and piece IDs follow from hit IDs. While it runs `AssistCx` asks no Continue, Fix-it or Next question of its own, and `isAnswering` holds an agent's reply until every answer has landed
- Workers (`client.ts`): one simulation worker for the live run, one assists worker for Continue, the long-gap ghosts' fallback and Re-place's own runs (`simulateAssist`), and a pool of assists workers (`assist-pool.ts`) for Auto place and the gap pieces, started on first use with `navigator.hardwareConcurrency − 1` workers, at most 6 (`assistPoolSize`); with fewer than 2 the assists worker answers them as before. Auto place (`prepareAutoPlace` and the `autoPlaceSearch` generator) and the gap pieces (`prepareGapSearch`, `gapSearch`) are split into stages of independent tries; the pool cuts each stage into chunks of about half a stage per worker, hands them to whichever worker is free, puts the answers back in the order the tries were asked and reduces them there, ties going to the first, so the choice is the one the single-thread `autoPlace` and `create*ForGap` make whatever the pool size or timing. The first chunk of a search to a worker carries the request (`searchTries` with `prepare`); the worker simulates the project up to the trials' end plus 0.25 s, the only part the checks read, prepares once and keeps it (`TWorkerMemory`), and later chunks carry only the tries. A gap search ends with `gapAnswer` on a worker that prepared it, for the ghost's track. One search runs at a time; a waiting request is replaced by a newer one of its kind, and `isCancelled` (Re-place's Stop) ends a search between stages. Every worker posts a simulation result with each marble's samples packed into a transferred `Float64Array` (`result-transfer.ts`); cloning a song's samples as objects took about 14 ms per result.

Frame bands and descent pace (`placement.ts`, `pace.ts`):

- `frameBand(project, laneId?)` with one marble is the film frame: 0.45 m wide at 9:16 at the original 0.65 m camera distance, scaled with the aspect and with `design.camera.distance` (0.59 m at the 0.85 m default), centred on the release. With several marbles each lane's band is 0.26 m wide (`LANE_HALF_WIDTH`, two zigzag columns of 9 cm bars a bar and a clearance apart), the lanes sit `LANE_SPACING` (0.26 m) apart ordered by release x and centred on the mean release, so neighbouring bands meet. Without `laneId` it returns the band covering every lane. Open hits report `outOfFrame` against their lane's band. Narrower lanes were tried with one world per marble (0.16 to 0.22 m, `references.md`, Narrower lanes): where bands overlap the other lane's pieces stand in the zigzag's way, the marbles stay about 0.26 m apart anyway and the builds that complete frame no closer.
- `paceRate(project)` is (1 − e) / (1 + e) · g · T / 2 for the default platform bounce e and the median interval T of all lanes' consecutive hits up to 0.8 s, with several marbles at least `columnRate(T, g)`, clamped to 0.15 to 0.8 m/s. `columnRate` is the rate whose drop per hit d leaves `COLUMN_CLEARANCE` (6.5 cm) between a bounce's top and the piece two hits back, which a zigzag passes under: with k = g·T²/2 the bounce rises (k − d)² / 4k, so d = 3k − √(8k² − 4k · clearance). Heights at a rhythm scale with gravity but pieces do not; at half gravity and 0.5 s the default bounce left 3.5 cm and marbles struck those pieces, and the rate becomes 0.30 m/s instead of 0.26. Full gravity at 0.5 s keeps the default bounce's 0.52 m/s. `descentPace(project, hits)` anchors y*(t) = anchorY − rate · (t − anchorTime) at the earliest hit with a dot. `simulate` returns it as `TSimulationResult.pace` for the camera; `paceAt` evaluates it. `PACE_LIMIT` is 0.25 m.
- `longGapThreshold(project)` is the interval at which a bounce at the pace would rise more than `MAX_BOUNCE_RISE` (0.4 m at Earth's gravity, scaled with `gravityScale`), between 0.6 and 2 s. Rise and pace both scale with gravity, so the threshold depends on the rhythm alone, about 0.68 s for 0.5 s hits. `findLongGaps` and Auto place use it. Auto place follows a launch into a long gap for 0.3 s / √gravityScale, since the hop rises the same 7 cm at any gravity and stays in the air that much longer.

Auto place, Continue and the gap helpers treat a project with several marbles as sharing one camera. Then Auto place solves each platform's bounce from the arrival velocity and the surface normal for the takeoff that lands the next dot on the pace (`paceBounce`), corrects it once by simulation when the dot misses by more than 2 cm, and rejects candidates whose next dot ends further than `PACE_LIMIT` from y* (or further than the current dot, plus 5 cm), whose path leaves the lane's band, whose next platform would not fit inside the band, or whose marble is not falling at `IMPACT_SPEED` at the next hit. A dot below the pace recovers half its offset per hit with at least 0.75 of the pace drop; a dot above returns at once. Narrow lanes leave angle windows of a degree or two (a 0.5 s flight moves the next dot about 4 cm per degree), so with several marbles the refinement and the fallback steps are 0.5°. When nothing passes, steps from −12° to 12° are tried (fast arrivals need nearly flat pieces), quarter degrees within ±3° for arrivals faster than 3 m/s, then the steps with the target 12 cm lower and higher, then −60° to 60°. The comfortable travel is two piece lengths, at most the band's half width, which centres a zigzag in a narrow lane. Before a long gap the bounce gives a 1.2 m/s hop that clears the piece into the switchback. Stray contacts with another marble count only up to that marble's next open hit, beyond which its path is unbuilt free fall. An angle whose run breaks another marble's hit that was on time up to that marble's next open hit is rejected (`crossesOtherLanes`); switchbacks, rails and tunnels for long gaps are never suggested when they touch another lane's pieces or marble. Continue drops ghosts that leave the pace, stops before a hit that starts a long gap and before a lane's last hit (whose fall past the other lanes only Auto place checks), and cuts the last ghost when a flat probe at the following hit would be blocked. A marble's path counts as unbuilt after its next open hit and after the launch into a long gap that nothing bridges yet. With one marble Auto place keeps the settling bounce that reaches the next hit at the steady speed of the default bounce, the 0.45 m frame and a soft pace.

Pegboard snapping applies to angles and to the bracket mount. The contact surface stays on the trajectory, so snapping never moves a hit off its time.

`createLoop` and `checkLoop` (`simulation/loop.ts`) make seamless loops. `createLoop` takes the loop start from the first sample at which a released marble is `0.75 * camera.distance` below its highest point, the end from the project end, both on a 1/30 s grid, and ghosts: each marble's samples from its release to just after the start, shifted by the loop length. Bars come from the optional `music.tempo` (`{bpm, beatsPerBar}`, set by MIDI import with four beats per bar). `checkLoop` reports `state` (ghost differs from the marble at the start), `entry` (first contact within 0.15 s of the start), `stillInView` (marble closer than 1.6 camera distances to its entry at the end), `lateRelease`, `reaction` (a hit within 0.25 s before the end), `movingPiece` (rotor angle modulo its blade symmetry) and `bars`.

Contacts record actual time, entity, marble and the approach `speed`: the marble's velocity toward the surface along the contact normal at the refined contact time, relative to a windmill blade's own motion. A hit is valid when its marble first touches its linked piece within 20 ms of the hit time at `IMPACT_SPEED` (0.3 m/s at Earth's gravity, scaled with `gravityScale`) or faster; a slower first contact is a resting or rolling contact and the hit is `missed` with `reason: 'resting'`. Unexpected contacts, including marble collisions, are reported separately.

## Blender bridge

The Rust host starts one Blender process per open project with the bundled worker. Requests and responses use the file mailbox proven in the desktop prototype:

- The host writes `{id, op, args}` to `.bridge/host-inbox/`
- The worker writes `{id, ok, result | error}` and progress files to `.bridge/outbox/`
- Agent tools write to a separate `.bridge/inbox/` that accepts only inspection and candidate previews

Operations:

| Operation        | Purpose                                                                     |
| ---------------- | --------------------------------------------------------------------------- |
| `apply_scene`    | Create or update holders, skins and keyframes from a scene description      |
| `preview_frame`  | Render an Eevee frame and an object ID pass at a time                       |
| `preview_clip`   | Render a short low-resolution clip                                          |
| `render_film`    | Start a film render with a preset in a separate Blender process             |
| `cancel`         | Cancel a film render job                                                    |
| `preview_render` | Start (or retarget) the background preview frames job in a separate process |
| `preview_render_cancel` | Stop the background preview frames job                               |
| `inspect`        | Report link states, detached objects and Blender-owned changes              |
| `preview_asset`  | Render a candidate asset in isolation                                       |
| `accept_asset`   | Copy an accepted candidate into the project library                         |
| `export_silhouette` | Write a simplified untextured mesh of a skin for the Compose view        |
| `save`, `shutdown` | Save `scene.blend` and close cleanly                                      |

Motion moves as a binary file rather than JSON. The app writes sampled positions and rotations as Float32 arrays into `.cache/motion/`, and the worker reads them with NumPy and writes F-curves with `foreach_set`. Keyframes are written at the render frame rate. Hit values become an animated custom property per piece.

Pieces in the scene description carry the resolved geometry from the simulation result (`TResolvedPiece` position, angle, `path` and `paths`), never raw transforms, so a free switchback (whose transform is its entry point) and a free rail (whose transform is its local origin) show where the physics put them. Each piece carries `hitTimes` (actual contact times of its linked hits), `contactTimes` (every marble contact start with it, starts within `CONTACT_MERGE` = 0.1 s of the previous one merged) and `musical` (the definition's flag). Both fields are additive; a worker that does not know them falls back to treating platforms as music pieces.

### Themes, reactions and camera

- `TSceneDescription.theme` selects a procedural theme in `blender/mm_worker/themes.py`: `pegboard` (flat toy colors, pegboard wall, wooden pegs) and `brass` (the reference look: lavender plaster wall, brushed brass bars on bent chrome brackets with round wall bases, chrome two-wire rails, satin tunnels, brass windmills, a glass marble with a swirl core in the lane color, one soft low sun from the upper left, a studio environment for metal reflections, AgX). Themes are data; materials are shared and created once, so Blender edits to them survive.
- A project theme reaches the worker as its base in `theme` plus `themeOverrides` (`TSceneThemeOverrides`, the applied theme's set colours). `themes.resolve_theme` lays them over the base settings: Wall paints the wall material (named per colour, so the shared base material stays untouched; Neon's grid follows the new wall), Light tints the sun, Background the world, Glow every Neon trim. `scene.apply` sets them for the apply with `themes.set_overrides`; the studio's `mm_theme` key includes them, so changing a colour re-themes the untouched studio, and the skin key includes Glow only when set. The Draft Preview resolves the same theme (`draftWall`, `draftPieceColors` with the overrides); Light has no draft equivalent, and a set Background draws around the frame
- The Wall and Lights layers reach the worker as `themeOverrides` (the layers' colours on top of the theme's, `appliedOverrides`) and the additive `wallKind`, `keyLight` and `lights` of the scene description. `themes.set_scene_look` lays `wallKind` and `keyLight` over the settings for the apply and joins `mm_theme`'s key, so a change re-themes the untouched studio and a reset returns the theme's values. `studio.apply_lights` keeps app-owned sun objects (role `studio.light`, `mm_light_id`) in the studio collection: a light the user edited in Blender keeps its values and is hidden rather than removed when the project deletes it, so undo shows it again; an untouched one is removed. `apply_scene` reports `lights: {created, updated, skipped, removed, hidden}`. A Neon back light stays the theme's, not a layer
- Default skins are built per theme and piece type (`skins.py`). A skin root carries a fingerprint of what the app built; the app rebuilds only unedited default skins of linked holders when the theme or parameters change. Edited skins, custom skins and objects outside the MidiMarble collections are never touched. Studio objects (wall, sun, world) are re-themed only while they hold what the app last wrote.
- Reaction times: `mm_hit` of a music piece (platform) follows its `hitTimes`; scenery (rails, tunnels, windmills, switchbacks) never has hits, so its `mm_hit` follows `contactTimes`. Windmill blade strikes from `contactTimes` also join the contact-frame snapping of the marble. A default windmill skin flashes its whole mesh (`mm_flash` on the skin root, strength 1.2) on each contact unless Design picks `none`; `glow` sets the strength.
- Reactions: a platform's bar is a child part whose drivers read the holder's `mm_hit`: it presses along its normal and tilts a few degrees around the bracket, springing back as `mm_hit` decays. An optional emission flash uses the `mm_flash` object property. Reactions never touch holders or their keyframes. `TSceneDescription.reactions` overrides the theme values. A piece's `reaction {preset, params}` from Design overrides the theme reaction for that piece: `none` adds no drivers, `press` (`press` m, `dip` degrees), `wobble` (`angle` degrees, `frequency` Hz; a decaying swing in the wall plane whose phase comes from `mm_hit` itself, `-ln(h)·τ` being the time since the hit) and `glow` (`strength`). Drivers are simple expressions, so they run without Python auto-execution.
- Library skins (`assets.py`): a piece with `assetPath` (`assets/<id>/asset.blend`) gets the asset's `MM_ASSET` collection as its skin. The worker appends the collection once per file into a template collection outside the scene (`MM asset · <path>`, fake user, images packed) and builds skins from object copies that share the template's meshes and materials. Appending rather than linking keeps everything the scene renders inside `scene.blend`, so packages move freely and film jobs render a saved copy without library paths; a changed `asset.blend` (size or modification time) reloads the template and rebuilds its skins. Skin layout: an empty skin root under the holder (its local transform is the user's offset), an `asset frame` empty that places the asset frame on the contact surface, and the copies. Box pieces put the asset origin at the centre of the top face with +Z along the contact normal, X along the length and Y into the wall; windmills put it at the hub with +Z toward the camera; rails and tunnels repeat the straight section along a curve on the top of the wire or the tunnel floor (Array and Curve modifiers). `fittedParams` from the asset's `manifest.json` scale the asset to the piece (`length`, `depth`, `thickness` per axis for boxes, `bladeLength` uniformly, `radius` across rails and tunnels), clamped to 4x. `MM_REACT_*` parts with `mm_reaction` get drivers on their delta transforms, so the modelled transform stays intact: `press` moves along the asset's -Z, `wobble` turns around the axis toward the camera, `glow` drives `mm_flash`, which the worker adds to the part's materials' emission strength. Switching between a library skin and the theme default replaces an unedited app skin and carries over the root offset; edited skins stay the user's. A missing or invalid `asset.blend` keeps an existing skin of that asset (otherwise the default is built) and is reported in `skins` as `missingAsset` or `invalidAsset`.
- Wall text (`walltext.py`): each `TSceneDescription.wallTexts` entry becomes a FONT object in `MidiMarble · managed` tagged with its entity's `mm_id` and `mm_role = 'text'`: centred on its wall position, extruded by `depth` (half each way, so the back sits on the wall), `size` as the letter size in metres, a colour material, facing the camera side and turned by its wall angle. `font` names a loaded Blender font (`Bfont Regular` is built in) or a font file, which is packed. Re-applying updates a text while it still matches what the app last wrote; an edited text is skipped, and a removed edited text moves to `MidiMarble · detached`. The ID pass picks texts by their `mm_id`.
- Camera: with `TSceneDescription.camera` (from `design.camera`) the worker bakes a follow camera in `camera.py`. Follow point: the weighted centre of the marbles in flight. Target: moved up to `lead` seconds ahead, smoothed with a zero-phase critically damped filter (time constant `0.04 + 0.5 * smoothing` s) and pulled along where a fast fall would leave the frame. The camera stands `distance` away at `pitch` from the wall normal, above and to the side of the run, so bars show their long sides and tops and the wall recedes like a floor, as in the reference. Image roll follows the run direction slowly plus a slow drift, so the columns turn between diagonal and near vertical. Shots set distance and extra roll with eased transitions and appear as `MM · <kind>` timeline markers. Several marbles widen the distance so all stay in frame. Lens 50 mm (`camera.lens` overrides it). The held ending: with `holdAfter` the marbles are read at the last hit and the follow point eases over a second to the middle of the last second of the run; with `holdFinish`, the mouths of the Finishes whose catch comes after the last hit (`heldFinishes` in `scene-builder.ts`, only Finishes `finishCatch` calls caught, of marbles that play last), it eases instead to half way (`FINISH_FRAME`) from the last hit's follow point to their mean, so the frame shows the last piece and the catch; `follow-camera.ts` bakes the same and `pnpm camera:check` compares them. Pitch 1.0 with a distance of about 0.65 m per 16 mm marble (0.95 m for the 1.5x kit of `reference-20`) matches the reference framing. Keyframes are baked on the studio camera, so Blender plays it without add-ons. A camera edited in Blender is taken over: `apply_scene` reports `camera: 'takenOver'` and regenerates only with `regenerateCamera`. `mode: 'manual'` leaves the camera alone.
- Contact frames: physics samples straddle each bounce and frames rarely fall on a hit, so a fast bounce would show the marble clear of its piece on every frame. The worker inserts an exact contact sample per hit (extrapolated from the incoming flight) and warps playback time locally so each hit lands on a frame of the 1/30 s grid (the frame rate's grid when it is not a multiple of 30). The shift is at most half a grid step (17 ms), and `mm_hit` uses the same snapped times so reactions start on the contact frame.
- Finish skins (`finish_spec` in `skins.py`) follow its wires like a switchback's: a cage of chrome wires as in the reference short's catcher, two under the marble's path either side of its plane, set back so the marble rests on both, and two guides at the marble's centre height either side of it along the catch wire, with ties every 2.5 cm and posts to round wall bases every 8 cm. A Chute's covered run-out is a clear acrylic tube (`clear_material`, alpha 0.14 with a clear coat, blended) around the marble's path with one thin chrome wire along its top, so the marble shows through it as it rolls away. Pegboard uses the same chrome and clear parts with wooden posts; Neon draws the wires as glowing tube edges (trim strength 2.4) on dark posts, without the tube. Colour by Note never applies: a Finish plays no note. `public/skins/<theme>-finish.png` are its Library previews (from Jingle Bells)
- Tunnels hide the marble: `mm_visible` on the marble holder is keyed 0 while the marble is fully inside a tunnel and drives the default skin's visibility.
- Loops: with `design.loop`, the scene builder adds `TSceneDescription.loop {start, end, blend}`, sets `duration` to the loop end and adds a ghost marble `<id>~loop` with `ghostOf` per marble. The worker stores the range as the scene property `mm_loop`, hides a ghost through `mm_visible` until its replay begins, leaves ghosts out of the camera follow, bakes the camera from before `start - blend` and blends the last `blend` seconds into the poses one loop length earlier with a smoothstep weight (rotations as quaternions), so the camera at `end` equals the camera at `start`.
- Switchback skins follow the bent physics wires point by point. Brass draws each wire as a pair of chrome wires either side of the marble plane, offset from the capsule line toward the side away from the marble (the outside of the bend, below the leg, outside the wall) with mitred vertex normals so the offset stays constant through the bend, with ties at the ends and wall posts at the ends and the middle of the bend. The marble side of a bent wire is the side it turns toward; a straight wire (the exit stop) faces the middle of the switchback. Pegboard draws one toy rod on the capsule line with wooden pegs at the same places.
- Decor (`decor.py`): `TSceneDescription.decor` as one object per layer in `MidiMarble · managed`, `mm_role = 'decor'`, `mm_id` its selection key so the ID pass picks it; meshes are built once per item and shared, in an asset's frame (origin at the back face's centre, +Z toward the camera). Asset decorations are an empty over copies of `MM_ASSET`. Timing reuses `walltext.write_timing`. Ownership follows titles: `mm_written`, a user's edit is left alone, and removing an edited one moves it to detached. `inspect` and `apply_scene` report `madeInBlender`: top-level scene objects with geometry the app doesn't own, with wall bounds. `apply_user_decor` writes their In, Out and Hidden with `keyframe_insert` on `hide_render` and `hide_viewport`, so their own animation stays, and restores what they had when the project stops setting them. `select_objects` selects by name. Their transforms are never written.
- Frame effects (`decor_effects.py`, `decor-effects.ts`, `DraftEffects.tsx`): `decor:snowfall` and `decor:garland`, catalog `effect` set, hang from the film camera after it is baked (`attach`, from `apply_scene`). The camera rolls 27 to 55° from the wall's up in Jingle Bells, so a wall-fixed line crosses the frame diagonally; only a camera child can stay at the frame's edges. One flat mesh each at 2 cm in camera space, `BLENDED`, unlit, coloured by the vertex attribute `mm_rgba`, gain `2^-exposure`: blended surfaces write no depth, so they sort over everything and take the wall's depth of field, not the blur they'd get 2 cm from the lens. A slot's `diffuse_color` stands in for Workbench. Snowfall: per-flake numbers on the mesh, one shared Geometry Nodes group places them from Scene Time alone, so any frame renders the same whatever came before; no handler, no simulation. Garland: a static strip, one baked `location[1]` curve from the camera's motion along its own up axis, scaled by near plane over wall distance, so it scrolls at the wall's speed; `garlandScroll` in TS mirrors it for the Draft Preview. Its soft part (halos, shadow) is a child `garland-glow`: Workbench draws outlines around every silhouette, turning soft things into rings, so Flat Light hides snow and glow (`flat_settings`), the ID pass all of them (`id_pass_settings`). Both are seeded by the layer's ID; a loop film snaps rates to whole cycles and the strip to whole pattern periods. They have `mm_role = 'decor'` and `obj.parent` the camera, no collider, no shadow
- Bloom (`apply_bloom` in `themes.py`): `MM · bloom` compositor group, Glare type Bloom at quality Low, threshold 2.2 in scene-linear light (above any lit wall here), then an amber multiply by distance from the frame's centre. Only while `bloom > 0`; a group the user made is theirs. Flat Light and the ID pass turn `use_compositing` off. Compositor math in Blender 5.4 uses the shared `ShaderNodeMath` family; `ShaderNodeMix` keeps a socket per data type, so its colour sockets are by index
- The worker needs an empty start scene: a scene that already has a World keeps it (a user's edit is theirs), so the theme's fill light doesn't apply. `render_decor_still.py` missed this, which made `.local/decor/stills` darker than Brass really renders.
- Skin model: `blender/mm_worker/skin_catalog.json` lists every built-in skin per element (`platform:copper`, `rail:chrome`, `marble:glass`: ids free of themes, with label, preview, Colour choices and default, reaction, variants) and each built-in theme's skin per element. The app imports the same file (`modules/design/skin-catalog.ts`), the worker reads it (`skin_catalog.py`, bundled by `tauri.conf.json`). `resolveSkinLook` and `resolve_look` say what an element wears: its own skin or its theme's part, each property from its override, from the part only while it shows the theme's skin, or from the skin; `blender/tests/skin_look_cases.json` holds cases both test suites run. Old `brass:<skin>` ids keep loading through `canonicalSkinId` / `canonical_skin` (`brass:nope` is Gold). Still `marble-project@4`: `skin.assetId` turned optional and `skin` gained optional overrides, project themes gained optional `parts`, and `parseProject` runs `migrateSkins`: ids take their new form, and `design.themeOptions.colorByNote` moves to the applied project theme's `parts.platform.colour`, or a new "Neon by Note" project theme on a built-in one. A scene description gains `themeParts` and per-marble `skin`; a description with the old `themeOptions.colorByNote` still reads as the theme's default.
- Skin builders (`skins.py`) dispatch on the skin's name, never the theme; `PieceFrame.look` is the resolved look. A platform's name picks a bar finish (`gold`, `silver`, `copper`, `dark`), a device (`device`: silver housing with a grille, a dome and end blocks in a finish, `device-copper` starting in copper, Variant another; `key`: dark housing with a white key; `knob`: dark housing with a red lens that glows on every hit unless On Hit says otherwise), or `pegboard` / `neon`. Colour: Marble tints a metal skin (`tinted_metal_material`), Skin on a toy skin shows bare wood, on a glowing skin a fixed cyan. On Hit: Glow on a piece with no moving part flashes the whole skin (`flash_ready`); Glow Colour swaps emission on a copy of a shared material (`glow_tinted`). Every skin keeps the collider's top face as its contact surface.
- Marble skins (`skin_materials.py`) are a sphere of the marble's radius with one material, so physics never changes with skin. Glass and Magic look into the sphere with a few samples along the view ray in the marble's space, like the parallax of codrops' Magical Marbles, instead of Eevee refraction or a volume: Glass samples twisted sheets in a blended surface, Magic three noise layers plus specks in an opaque dark orb, moved by a Value node driven by the frame. Chrome and glass reflect a small studio painted in camera space, so they look alike on every wall. Flat Light draws them in `diffuse_color`. The theme's default marble is `marble:contrast`, today's Pearl or Deep by contrast (Brass's keeps its older glass core); Pearl and Deep force a tone.
- Extra skin properties: a manifest's optional `properties` (`{name, type: number|colour, default?, min?, max?}`) become rows in the Skin section, stored in `skin.properties`. `assets.apply_properties` writes each value to the material inputs and the Value or RGB nodes of that name on a per-skin copy of the material; a material without one ignores it. Deliberately simple: no driving, no parts.

### Film render

`render_film {preset, engine?, outputPath, audioPath?, samples?, jobId?}` saves a copy of the live scene to `renders/.jobs/<jobId>/scene.blend`, starts a background Blender on it with `blender/render_job.py` and answers with the job right away, so the live worker stays responsive. Presets: Draft 720p 30 fps, Fast 720p 30 fps, Balanced 1080p 30 fps, Best 1080p 60 fps, by the short side (portrait 9:16 gives 1080x1920). Draft ignores `engine` and renders with Workbench (`workbench_settings`: material viewport colours, shadows, cavity, outlines, Standard view transform, no depth of field or motion blur) and writes JPEG frames; the started and finished job report `engine: 'workbench'`. Output frame i shows time i / fps, independent of the keyframe rate. The job writes progress to `.bridge/outbox/<jobId>.progress.json`, renders PNG frames, muxes them with the soundtrack WAV into an MP4 (H.264, AAC) with FFmpeg (or with Blender's own FFmpeg through the sequencer when no binary is found) and writes the response envelope to `.bridge/outbox/<jobId>.json`. The host reads both with `blender_job_poll`. A scene with `mm_loop` renders frames `start + i / fps` up to the frame before `end`, so the MP4 repeats seamlessly; `renderFilm({loop})` writes the matching soundtrack (`renderProjectAudio` with `loop`: lanes from the loop's hits rendered 3 s past its end and folded onto the start, or a recording cut with a 50 ms crossfade into the audio before the start). `cancel {jobId}` sets a cancel flag the job checks between frames and stops the process after a grace period. The job also stops when the app exits, and the live worker reports jobs that end without an answer. `renderFilm` in `src/modules/blender/render-film.ts` writes `renders/soundtrack.wav` from `renderProjectAudio` and follows the job. A film is always rendered inside the package; with `destinationPath`, `renderFilm` copies the finished film to the path chosen in the save panel through the host command `copy_file_out(packagePath, relativePath, destinationPath)` (absolute destination in an existing folder, copied through a temporary file and a rename) and returns that path.

Scene structure in Blender:

- `MidiMarble · managed` holds app-owned holder empties with locked transforms
- Each holder parents its skin, so Compose transforms move the skin and Blender offsets stay local
- `MidiMarble · detached` receives skins of deleted pieces
- Everything else belongs to the user

### Background preview frames

Film playback shows Blender frames rendered in the background, like Final Cut's background render (`blender/mm_worker/live_preview.py`, `blender/preview_job.py`, `src/modules/design/LivePreviewCx.ts`, `live-preview.ts`). After every scene sync `DesignCx` names the applied scene with `sceneSignature` (FNV-1a over the scene description and every motion file, plus a counter for applies that change Blender without changing the description: Discard Blender Changes, Reset Camera) and `LivePreviewCx.sceneApplied` starts `preview_render {signature, fps: 30, width: 360, order, refine}`. The worker saves a copy of the scene to `.cache/preview-frames/<signature>/scene.blend` and starts a background Blender on it, like `render_film`; the same signature while the job runs only replaces its target. Frames are every `step`-th scene frame (a 60 fps scene previews at 30 fps), named `00042.jpg` (Flat Light: the Draft export's Workbench settings with 5 antialiasing samples) and `00042.fast.jpg` (Fast lighting: Eevee, 8 samples), JPEG quality 82, 360 px wide at the film's aspect (360×640 for 9:16).

The app owns the order. `previewFrameOrder` lists the playhead and 3 s ahead, then outward one frame ahead and one behind in turn; `refineFrames` lists 1 s from the playhead for the Fast pass, only while paused (Fast frames cost about 15 Flat Light ones). The host writes them as `target.json` with `blender_preview_target` when the playhead moves half a second or playback starts or stops, without the worker's queue; the job re-reads it between chunks. A chunk is the first missing frame of `order` (else of `refine`) and its missing neighbours, up to 24 Flat Light or 8 Fast frames, rendered as one animation render, which keeps Blender's render scene between frames and makes a frame about four times cheaper than a still render (about 20 ms against 65-80 ms at 360 px; the cost is the per-render setup, not the pixels). Each frame is rendered as `.partial-<frame>.jpg` and renamed, so the app never reads a half-written file. The job writes `status.json` (`state`, `pid`, counts and ms per frame of each level) after every chunk and exits when both lists are done; `LivePreviewCx` starts it again when the playhead reaches missing frames. `blender_preview_cancel` writes `cancel` (checked between chunks); leaving Film, turning Live Preview off, a new signature and the worker's shutdown stop it; it also stops when the app exits. `blender_preview_frames` lists the frames of each level and the status; the app polls it every 400 ms while the job runs.

Invalidation is the simplest correct rule: any scene change is a new signature and a new folder, so no frame of an older scene ever shows. Keeping frames before the first changed time was left out: a change at one time moves the follow camera and the marbles' paths around it, so the safe boundary needs the camera and simulation diff, not the description. Undo returns to a signature whose frames are still there; the worker keeps the newest 3 signature folders. Edits made in a Blender window reach the preview with the next scene sync. The packaged project leaves `.cache` out.

Flat Light (`workbench_settings` in `render.py`, shared by Live Preview and the Draft export) is flat lighting through the scene's own view transform and look, plus per-theme exposure offset and sheen (`themes.flat_look`, measured against Fast); metal renders darker (`FLAT_METAL`) and Neon's glowing materials brighter (`FLAT_NEON`) as it has neither reflections nor emission. `pnpm blender:preview` compares the wall per theme (`check_flat_colors.py`).

`DesignView` draws in the app while playing and while paused when Blender's still is not at the playhead but a frame is: the Draft Preview with `LivePreviewFrame` over it and `SelectionOverlay` above that, a canvas that follows `$playhead` outside React, draws the nearest frame within one frame (Fast before Flat Light) once decoded (`PreviewImageCache`, 150 images, least recently used out, decoding 1 s ahead), keeps the last frame 0.25 s while the next decodes and fades over 140 ms to the Draft Preview where nothing is rendered. The ruler's render bar draws `renderedSpans` of each level.

## Agents

Agents connect over MCP only (design-language.md, Round 9; see MCP below). The person's own Claude Code, Codex or Claude app starts `midimarble mcp`, which talks to the open app, so an agent has the same commands a person has. Every edit is one named Undo step, shown live; the Agent menu and the canvas pill show who is connected and what is running, and Stop ends a running Build Track, Re-place or export.

The package's `agent/` folder (`agents/folder.rs`) holds what the project wants from agents: `AGENTS.md`, `references/` (`set_references`), `notes/`, `scratch/`, and `runs/`, which logs each MCP session. New skins and decor come in with `add_asset`, and `preview_frame` renders a still for the agent. `agents/brief.rs` and `mm_preview.py` wrote the brief and checked the asset for the removed in-app chat; nothing calls them now. An older project's `candidates/` folder stays where it is and nothing reads it.

## Marble skins

A marble's `skin` reaches the worker through the scene description as a piece's does. A built-in id resolves in `skin_catalog.resolve_look`; a library item comes with `assetPath`, and `scene.ensure_skin` then builds it as `assets.create_asset_skin` does for a piece, with the `sphere` layout: origin at the marble's centre, even scale from `fittedParams.radius`, the tunnel visibility driver on each model. `blender:design` checks this from the command on (`scripts/export-marble-skin-scenes.ts`, `blender/tests/check_marble_look.py`), reading the materials and the rendered pixels. The default skin, `marble:contrast`, is pearl or deep by contrast; a deep body is as light as it can be and keep 3:1, between `DEEP_LUMINANCE` 0.05 and 0.09.

Camera **Sway** (`design.camera.sway`, absent is 1) scales the view's side angle from straight below the target and its own roll in `camera.view_turn` and `viewTurn`; a shot's roll stays. Wall kind **plain** is a flat material with no texture.

## MCP

`midimarble mcp` is the app binary as a local stdio MCP server (`src-tauri/src/modules/mcp`). `main.rs` branches before Tauri starts, so there is no window and no second app. JSON-RPC is hand-written (`protocol.rs`) with newline-delimited messages; stdout carries only protocol. The process answers `initialize`, `tools/list` and `get_guide` itself (guides are markdown in `mcp/guides/`, built into the binary) and sends every other tool, one connection per call, over a Unix socket to the running app.

- **Socket:** `~/Library/Caches/MidiMarble/mcp-<binary>[-debug].sock`, computed from the binary's own name in both processes, so a bundled app and a debug build don't meet. The folder is 0700 and the socket 0600; there is no network port. A live socket is left alone and a stale one replaced. `MM_MCP_SOCKET` overrides the path for tests. With no socket the server answers that the app isn't open or Enable MCP is off.
- **Enable MCP** (Agent menu and Help menu, `mcp.json` in the support folder) is on by default: the socket exists only while the app is open and only this user can reach it, and every edit shows in the window with Undo, so connecting needs no setup step. Turning it off removes the socket.
- **Bridge:** a connection thread emits `McpRequestEvent` to the front end and waits on `mcp_respond`. `McpCx` runs calls one at a time through `runTool` (`src/modules/mcp/mcp-tools.ts`). `imagePath` blocks become base64 image blocks in the host. The host appends each call to `agent/runs/mcp-<session>.jsonl`, the benchmark record.
- **Edits:** `StudioCx.runAgentStep` folds everything a call does into one undo group named "Agent: …", shown in a notice with Undo and in Edit > Undo; notices raised meanwhile become the reply. Each reply waits for the run to match the project (at most 8 s) and carries the hit summary and problems from `preflightExport`, the window's model. A pointer held down, an open alert or the Import Song sheet makes an edit wait 2 s, then say busy.
- **Tools** stay these ten; a new command needs no new tool. `project.execute` takes project commands plus `placePiece`, `applySkin`, `placeDecor` and `scatterDecor`, which expand in `project-commands.ts`. Commands that ask through a panel take `args.path` instead (`ARGUMENT_COMMANDS`) or say which tool replaces them.
- **`preview_frame`** always renders through Blender's `preview_frame`, draft at 540 wide and blender at 1280. The Draft Preview can't be captured: it is a canvas with SVG and DOM above it, and only exists in Film.
- **Connect** (`connect.rs`, `McpCx.toggleConnection`, words in `mcp/agent-connect.ts`): `mcp_connect` finds `claude` or `codex` in a fixed list of install locations, then the Claude desktop app's newest bundled copy, then the login shell, as a GUI app's PATH reaches none of them. It runs the tool's `mcp remove` (failure ignored) and `mcp add … -- <binary> mcp` on a background thread with stdin closed and 20 s for both, where `<binary>` is `current_exe`. With no tool found it copies the command text with the plain name, through `pbcopy`, since a native menu item has no user gesture for the web clipboard. `mcp_connections` reads `~/.claude.json` and `~/.codex/config.toml` read-only and compares the listed command with this binary; only the tools write those files. `McpCx` turns on Enable MCP after a Connect. An agent can't run these commands (`PERSON_COMMANDS` in `mcp-tools.ts`).
- **Rules for agents** travel in `initialize`'s `instructions` (`protocol.rs`), as no folder holds an `AGENTS.md`: `get_guide` first, own files in the project's `agent/` folder, the film only through the tools.

**What `run_command` answers.** Every reply says `changed`, whether the call made an Undo step, and `edit.undo` and `edit.redo` name what they took back in `undid` and `redid`. `project.execute` checks each command strictly (`commandProblem` in `mcp/project-commands.ts`): an unknown field is an error that shows the command's shape, a component's value is checked against its schema, and commands that leave the project as it was answer `changed: false` with no Undo step. `args.select` refuses a key the project doesn't know; `edit.select` selects and does nothing else. `build.track` answers when done, or at once with `wait: false`, and `build.rebuildFrom` answers when done (region-local in `ARGUMENT_COMMANDS`: it runs the same `AssistCx.buildTrack` from `rebuildTarget`); meanwhile `get_state.building` gives progress and `get_state.lastBuild` the result. `get_state` and `build.stop` are answered outside the front end's queue, so they work during a long call on another connection, and other edits answer that Build Track is running. An agent's `build.next` places a gap piece in the same call instead of showing a ghost, and `settled` waits for `AssistCx.isAnswering`, so the reply and the next call see the finished step.

**Who is connected.** Once a client has initialized, the stdio process holds one more socket connection open for its whole life, sending one `__presence` line with its session and clientInfo name (`keep_presence`, retrying every 2 s while the app is away). `tools/call` can't reach that name, since it forwards only listed tools. The host keeps these by session (`ConnectedClients`) and emits `McpClientsEvent` when one joins or hangs up; `mcp_status` has the same list. Turning Enable MCP off hangs up on them, and they come back when it's on. `agentStatusLine` (`mcp/agent-presence.ts`) words it, with product names for known clients.

**An agent in the window.** `McpCx.answer` wraps each queued call: `presenceLabel` says what it is doing (null for a read), `AgentPresenceCx.begin` raises the pill for the call's life plus 1.5 s, and `runProjectCommands` refines it from its commands ("Placing Platform 12"). A `build.track` with `wait: false` holds the pill until the build ends. `$current` changes only when a call starts, ends or relabels. `McpCx.stop` (Stop) bumps `stopEpoch`, stops a Build Track or Re-place if the call is in an agent step (a person's own build is theirs) and cancels an export the call started. A call sees the epoch change: one still waiting for its run doesn't edit, a queued one is refused, and each reply says the person pressed Stop. Calls arriving within 1.5 s are refused too, since they were sent before the agent could know.

**What an edit touched.** `McpCx.watchEdits` diffs each history change made inside an agent step (`touchedKeys`, selection keys of changed entities, Wall, lights, Decor, shots, Camera and Song) into `$touched`, entries lasting 1 s. `AgentTouched` in `ComposeCanvas.tsx` and `AgentTouchedOverlay` in `DraftPreview.tsx` draw the selection's outline with a CSS fade (no fade under Reduce Motion); the film one follows `$frame` only while something is marked. Sidebar sets `data-agent-touched` on the rows directly, so the list doesn't render.

**`get_state.selection`** is resolved (`resolveSelection` in `mcp/mcp-state.ts`): a hit with its marble, time, note, status, dot and platform (id, place, angle, length); a piece with its place, angle, length, params and hit; marbles, titles, lights, decor, shots and other layers with what identifies them. Every item has a `key` for `args.select`. Edit replies still give `selection` as keys. `get_state` also passes `building` and `lastBuild`, which the build's docs promised.

**Project commands check against the project** (`mcp/project-commands.ts`): shape first, then ids and values (`valueProblem`): a skin must exist and fit its element, a theme must exist, ids must be there, a title's font must be usable. `setDesign` merges into `camera`, `wall` and `lights`, and `setComponent` into `marble`, `skin` and `wallText`, so an agent names only what changes. An error names the field that is wrong and shows that field's shape. `list_commands` answers with `skins`; `get_state` holds the camera, each marble's colour, radius and skin, what the wall and Key Light show with `own` on top of the theme, titles and Pack themes. A Pack theme's id works in `setDesign`, which copies it in as the Theme picker does.

## Package

```txt
Song.marble/
├── project.json   # versjon `marble-project@<n>`
├── scene.blend
├── audio/         # imported sources
├── assets/        # project library items
├── candidates/    # empty; an older project's agent results stay here, unread
├── agent/         # AGENTS.md (this project's goal and rules), references/, notes/, scratch/ (left out of Save As), runs/
├── renders/       # previews and exports
├── .cache/        # motion, waveforms, silhouettes; regenerable
└── .bridge/       # runtime mailbox
```

The package is registered as a macOS document package so Finder shows it as one file. Every stored path is package-relative. The global library lives in the app's support folder with the same item layout and is registered as a Blender asset library for the dedicated process.

Library item:

```txt
<item-id>/
├── manifest.json  # versjon `marble-asset@<n>`: role, piece type, parameters, contact surface, reactions
├── asset.blend    # textures packed
├── thumbnail.png
└── silhouette.glb
```

The `agent/` folder is created on first agent use. References are the images and `references.md` in `agent/references/`; `set_references` replaces them and the Scene inspector shows them only when present. Films and Packs leave `agent/` out.

### Packs

A Pack is a `.marblepack` folder: `pack.json` (`marble-pack@1`: id, name, version, optional description, author and link, and the items), `themes/<id>.json`, `assets/<id>/` as library items, optional `picture.png`. Packs hold themes, skins and decor only, nothing with a hitbox. `pack.rs` validates ids and refuses symlinks.

By default no Pack is added. Add Pack… lists the Packs in the app bundle (`packs/`, resources) and any file through Import from File…. Adding copies the Pack to `Packs/` in the app's support folder, for every project on this Mac, and changes nothing in the open project. `addedPacks` in `library-client.ts` is the list Insert, the tiles and the Theme picker read; `addedBuiltInDecor()` gives a bundled Pack's `source` items, built-in procedural decor ids that have no asset until real ones exist.

Only what a project uses is copied into it, as an ordinary library item or project theme. Each copy records its origin `{ packId, packName, version, author?, link? }` (`SPackOrigin`), so a project on another Mac still names the Pack: the line reads "Christmas Pack · Not Added" and opens that Pack's card. Items keep rendering either way. `version` changes nothing yet; it is kept so updates can be told apart later.

## Menu bar

The host builds the macOS menu bar (`src-tauri/src/app/menu.rs`). Before the web view loads it shows the app menu, AppKit's Edit items and Window. Once mounted, the front end (`src/modules/studio/native-menu.ts`) sends the menus laid out from the command registry with `menu_set_bar` (again when Recent changes) and later changes of titles, enabled and checked states with `menu_update_items`, diffed and batched. Choosing a command item emits `menu-command-event` with its id (`file.save`, `help.quickHelp#help` for a second item of a command, `recent:<path>`, `recent.clear`); the front end runs the command through the registry. Cut, Copy, Paste and the app and Window menus are AppKit's predefined items and never reach the front end. Save As… copies a package with `copy_project` (everything but `.bridge/`), Clear Menu calls `clear_recent_projects`. The `exports_typescript_bindings` Rust test writes the specta bindings without starting the app (`MM_BINDINGS_OUT=<path> cargo test exports_typescript_bindings`).

## Testing

- **Unit:** Vitest for schema, migrations, commands, history, lane assignment and piece parameters
- **Fixtures:** example projects simulated headless in Node. Each fixture states its expected hits and fails when any hit misses 20 ms.
- **Blender:** headless checks build a scene from a fixture, read the keyframes back, compare contact frames with hit times and render a frame
- **UI:** the UI development surface runs in a browser with a mocked host. The built-in browser and computer use are allowed for milestone checks of this app, including the native window and Blender.
- **Reference films:** rendered at milestone ends and compared side by side with the references
